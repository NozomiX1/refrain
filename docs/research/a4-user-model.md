## 1. 各家建模哪些维度

## 2. 用户要不要单列

| 做法 | 谁 | 理由 |
|---|---|---|
| **单列** | Magic Context（单独的流水线、跨项目画像）、Hermes（USER.md）、Letta（human 块）、CC（user 类）、ToM-SWE（独立的 ToM agent） | 跨项目共享；可以单独审查；可以单独设门槛（Magic Context 要求 ≥3 次） |
| **不单列** | trace-memory（用户偏好就是 global 的 constraint）、Pi OM | 少一套规则；偏好往往和具体场景绑在一起 |

**结构化 schema 的教训：** User as Code 用类型化的 schema 存用户，增量改写时一个会话丢掉了 10 个百分点；"LLM 会把事实当字符串塞进 notes 字段"，schema 变成了摆设。LangMem 的"画像"也要求事先定好 schema。trace-memory 和 Magic Context 删减类别的经历，也指向同一个方向：**维度适合当检查清单和标签，不适合当固定的槽位。**

## 3. 顺带的发现：CC transcript 里的 `user` 不一定是我（影响 ADR-0004）

Letta Code 的初始化流程（`initializing-memory/SKILL.md`）专门提醒：
- "在 Claude Code 或 Codex 的 worker 会话里，`user` 条目可能是父 agent 写的提示词；harness 注入的 `<system-reminder>` 不是人说的话。"
- "重复不能证明作者是谁：一个模板在 50 个会话里复用，就会重复 50 次。"
- "提升任何关于'人想要什么'的说法之前，先确认引文是谁写的。不确定就作为观察到的模式存下来，并写明不确定。"

ADR-0004 规定"证据只认我本人的条目"。但 CC 的 transcript 里，role 为 user 的条目可能是：我本人的消息、工具结果、hook 和系统注入的内容、子 agent 收到的提示词、我粘贴进来的文本。**所以提取时必须先判断作者是谁**，这一点归入 B 段（新问题 B8）。
