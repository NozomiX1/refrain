# 0001. 项目定位

- 状态：采纳（2026-10-22）
- 日期：2026-10-22
- 相关：[positioning.md](../positioning.md)（定位的当前全文）· [research/scan.md](../research/scan.md)（证据）· [archive/memory-plugin.md](../archive/memory-plugin.md)（最初的讨论稿）

## 背景

最初的讨论稿（2026-10-19）把项目定位为"低成本、面向对齐、开箱即用（冷启动）的 Claude Code 记忆系统"。那个定位没有经过调研，只是从我自己的痛点推出来的。

2026-10-22 重新梳理了定位，确定了以下几点：
- 要交付的价值：跨会话遗忘、对齐成本、压缩丢信息、记忆的影响看不见。
- 约束：成本，不是功能。
- 用户：先服务我自己。

随后做了一轮横向扫描，覆盖 9 个 CC/Pi 记忆方案、4 个通用记忆层和十几篇 2026 年的论文，用来检验差异化假设 H1–H5。

扫描发现最初的定位有两处站不住：
- **"建模用户"不是差异点。** 几乎每家都有用户画像，CC 自带的 auto memory 就有 `user` 和 `feedback` 两类。
- **"压缩时不调模型、直接渲染"已经是共识。** Pi OM、Magic Context、trace-memory 都这么做。

## 考虑过的选项

1. **保留最初的定位**（低成本 + 对齐 + 冷启动）
   - 问题："对齐"的核心是建模用户，而这已被别人做了；"低成本"太笼统，别人也在优化成本。
2. **以纠正为中心**（Claude 提议）
   - 写入、展示、评测、成本都围绕"用户纠正"这一个单元来设计。
   - 问题：太窄。记忆是会影响将来的东西，纠正只是其中一种，习惯、偏好、约定同样重要。
3. **不自己做，转为给现有方案贡献**，比如 trace-memory 或 claude-mem
   - 我在定位草稿里定过规则：H1–H5 全部被推翻，就考虑这条路。实际上 H3、H4 成立，其余三条改写后也站得住，所以没有触发。
4. **按扫描结果重新定义的四个差异点**（选这个）

## 决定

定位的全文见 [positioning.md](../positioning.md)。这里只记录核心：

**一句话：** 一个给 Claude Code 用的跨会话记忆系统，让模型越用越懂我，而记忆系统本身的消耗不超过它省下的。

**四个差异点：**
1. **忠实且被遵从的用户模型**：每条记忆都有我本人的原话作依据；能强制执行的，用 hook 强制执行。
2. **使用归因**：知道模型这一次实际用了哪条记忆。
3. **可量化的低成本**：在真实使用中报告记忆开销比。
4. **冷启动**：回填历史 transcript。

**必须做好，但不算差异点的：** 压缩时只渲染、不调模型；保持 prompt cache 稳定。

**范围：** 只做 CC，不做团队共享，不做游戏适配，和 CLAUDE.md 共存。

## 理由

- **每个差异点都对应扫描中发现的一个具体空白：**
  - 用户画像会编造：研究称约四成内容超出证据（第三方摘要的数字）。
  - 记住了不等于照做：用 Mem0 时，57.5% 适用的偏好仍被违反。
  - "注入了哪些"已经有人显示，"实际用了哪条"没人做。
  - 在 CC 的真实使用中，没人报告开销比。
  - CC 场景下没人回填历史。
- **四个差异点都可以测量**，可以直接变成评测指标：
  - 1 → 编造率、遵从率
  - 2 → 归因准确率
  - 3 → 记忆开销比
  - 4 → 回填后多快开始见效
- **差异点 1 和 2 延续了"可验证、可追溯"这条主线。** 记忆既能查到出处（来源），也能查到去处（归因）。
- **差异点 1 用 hook 落地，是利用了 CC 的特有能力。** 官方文档也说，要无论模型怎么决定都阻止某个动作，就用 PreToolUse hook。

## 后果

好的方面：
- 差异点可以测量，评测方案有了明确的靶子。
- 和 CC auto memory 的区别能说得很具体。

要付出的代价和风险：
- **差异点 2 的可行性未知。** 注入了哪些记忆是确定的，但判断模型"实际用了哪条"很难。如果实验证明做不到，定位就少一条腿。
- **差异点 1 的"只依据我本人的原话"，和愿景里的"了解我的行为"有张力。** 有些偏好我从来没说出口，只是默默接受了，或者用行动表现出来。只认原话会漏掉这类信号。这个张力要在问题清单里单独讨论。
- **hook 强制执行可能过度拦截，**反而让人烦。哪些记忆适合强制执行，需要单独设计。
- **差异点 3 要求从第一天就记录 token 消耗**，测量本身也是工作量。
- **冷启动受限于 transcript 的保留期。** CC 会按 `cleanupPeriodDays` 删除旧会话。
- **"必须做好"的部分**（压缩接管、缓存稳定）**不会因为不算差异点而变少**，工作量并没有减少。

## 什么情况下推翻

- 实验证明使用归因不可行或很不准 → 新写一份 ADR，去掉或改写差异点 2。
- 找到一个 CC 方案，已经做到用户模型忠实且被遵从 → 重新评估差异点 1。
- CC 官方的 auto memory 补上了跨项目、整理和来源 → 重新评估 H4，以及项目的必要性。
- 我自己用了一段时间后，发现最痛的地方不在这四点 → 回到定位重新讨论。
