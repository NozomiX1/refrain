# 0009. 谁来写：只有后台 worker 写，按量触发；现状随 worker 更新，压缩只拼装

## 背景

B1 的问题是：记忆由主模型在对话中当场写，还是由后台 worker 写。ADR-0007 还给它加了一个要求：我说"记住……"时，要能立即生效。

调研了 7 家（见 research/b1-writer.md）。大多数项目两种方式都用：主模型留一个窄入口，后台负责大部分提取。只有 trace-memory 和 claude-mem 完全不让主模型写。

我一开始提的方案是：只让 worker 写，主模型保留一个"标记"工具，用来立刻唤醒 worker；压缩和会话结束时也触发 worker。我本人否决了这个方案，理由有三条：

- **不需要立刻记。** "记住……"本来就在上下文里。worker 处理到那一段时，自然会提取出来。
- **压缩时不需要触发。** worker 平时已经处理了大部分会话。压缩时还没处理的部分，原样保留就行。压缩时最近的上下文本来就最重要，这样一举两得，而且不用等。
- **压缩应该只是换一段上文，根本不需要等。** 那么现状也不能和压缩、会话结束绑定。

## 考虑过的选项

1. 主模型当场写（CC auto memory、Hermes、Letta 的主模型部分）
2. 主模型标记，worker 写；压缩和会话结束时也触发（我最初的提议）
3. **只有 worker 写，只按量触发；现状随 worker 更新；压缩只拼装现成的东西**（选这个）

## 决定

**1. 只有后台 worker 写记忆。** 主模型不写，也不标记。我说"记住……"属于原话，按 ADR-0004，说一次就够。worker 处理到那一段时会提取出来。

**2. worker 只按量触发。** 每轮结束时检查一次，新内容攒够一定量就运行，阈值靠实验定。压缩和会话结束都不触发它。worker 读的是磁盘上的 transcript，不是上下文，所以压缩不会让它丢掉任何东西。

**3. 不漏处理。** 每一段 transcript 最终都要被处理一遍，包括会话结束时剩下、还没达到阈值的尾巴。这些尾巴在下一次 worker 运行时补上。

**4. 现状随 worker 一起更新。** worker 每次运行，提取长期知识的同时，在同一次调用里把现状也更新一遍。ADR-0008 的重写规则（每一项都要有交代）不变，变的只是更新时机。

**5. 压缩只拼装，不调模型。** 压缩时把四样现成的东西拼起来：长期知识、最新的现状、已处理部分的摘要、还没处理的原文尾巴。现状可能比最新进展落后一点，这段差距正好就在原文尾巴里。

**修订 ADR-0007：** 原来的前提是先补上"'记住……'立即生效"，再关 auto memory。现在改为：**worker 保证每一段都会被处理（包括关掉的会话的尾巴），再关 auto memory。**"立即生效"的实际含义变成：在当前会话里，它就在上下文中；在之后的会话里，它在下一次 worker 运行之后生效。

**修订 ADR-0008：** 现状的重写，从"压缩前和会话结束时触发"，改为"随 worker 每次运行一起更新"。

## 理由

- **单一写入方。** ADR-0006 要求写入时裁决：每写一条，都要先看相关的旧知识。这只在一个地方发生，就不会出现 Hermes 那种"同一件事被写进两个地方"的问题（issue #30220）。
- **主模型不分心，也不花贵模型的 token。** LangMem 说过，当场写"给 agent 完成用户需求又多加了一道障碍"；后台写"召回率更高"。这对差异点 3（低成本）有直接好处。
- **原文就是事实来源。** worker 读的是 transcript，压缩不会破坏它，所以不需要抢在压缩之前处理完。trace-memory 也是这样：压缩时放进去的，是最近还没提取的原文。
- **压缩不调模型，已经有先例。** Pi OM 的 README 写着："压缩时，你得等一个模型去重写过去，大会话里要等好几分钟。"它的做法是用准备好的记忆，不调模型，也不等 worker。trace-memory 在 CC 上，用插件接口替换 CC 的总结，也不调模型。

## 后果

好的方面：
- 压缩不用等。
- 主模型完全不用管记忆的事。
- 写入只有一条路，便于做校验和统计。

要付出的代价和风险：
- **现状更新得更频繁了。** 这一点我自己也纠结。缓解办法：worker 发现现状没变时，直接输出"没变"，不重写。实际开销到 E 段再测。
- **有延迟。** 会话最后一句说的"记住 X"，要等下一次 worker 运行时才进入长期记忆。如果我紧接着去另一个项目开新会话，那边暂时还看不到它。
- **长会话里的新知识。** 我一个会话会跑很多天。会话中途新写进去的知识，压缩后有没有重新注入，留给 C1/C2 去定。不过按决定 5，压缩时会拼进长期知识，所以只要拼装时用的是最新版本，这个问题就能自然覆盖。
- **能不能在 CC 里做到，还没验证。** "替换 CC 的压缩内容"依赖插件接口，要到 D1/D2 实测。如果做不到，退路是用 PreCompact 注入现成的内容，让 CC 的总结去参考它。

## 什么情况下推翻

- 实验发现我说的"记住……"经常在 worker 处理之前就需要用到（比如我关掉会话立刻开新会话），延迟带来了实际问题 → 加一个轻量的立即触发通道。
- 现状频繁更新的开销太大，或者反复改来改去导致内容不稳定 → 改为只在 worker 发现阶段、待办或授权发生变化时才更新。
- CC 插件接口不支持替换压缩内容 → 重新评估压缩时要不要等一次模型调用。
