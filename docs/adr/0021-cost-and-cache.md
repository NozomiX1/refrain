## 背景

ADR-0020 把"记忆开销比"定为差异点 3 的指标，E1 要回答怎么算。我用的是 Pro 订阅。Claude 原本打算按订阅额度来算，我没有采纳：额度换个账户或换个套餐就不适用了。按模型的 token 开销来算更合适，因为同一份数据可以拿来估算换成不同模型要花多少钱。

我查过，Pro 也是 1 小时缓存。本会话的 transcript 可以印证：缓存写入记的全是 `ephemeral_1h`。Magic Context 文档里"Pro 只有 5 分钟"的说法，至少对我的账号不成立。

CC 的 transcript 会把每次请求的用量按类型分开记：输入、5 分钟缓存写入、1 小时缓存写入、缓存读取、输出。

## 决定

### E1：开销比

**统一按 API 等价成本计算：** 每类 token 的数量乘以对应单价，再加起来。

| token 类型 | 单价（以正常输入价为 1） |
|---|---|
| 输入 | 1 |
| 5 分钟缓存写入 | 1.25 |
| 1 小时缓存写入 | 2 |
| 缓存读取 | 0.1 |
| 输出 | 模型的输出单价 |

- **开销比 = worker 的成本 ÷ 主会话的成本**，可以按会话统计，也可以按时间段统计。
- **单价表单独配置。** 换成别的模型的单价重新计算，就能估算"worker 换成 Haiku 或 Sonnet 要花多少"。限制：fork 必须和主会话用同一个模型，否则缓存用不上，所以这种换算只对新开的 worker 成立。
- **只靠 transcript 识别 worker 的用量，不另记日志：**
  - fork 型 worker：派生时用固定的描述（比如 `memory-worker`），它的 transcript 在子 agent 目录下；
  - 新开型 worker：固定在一个专用目录里运行，它的 transcript 会落在单独的项目文件夹里。
- **压缩本身的成本记为 0**：压缩不调模型，实测 5ms（D-b）。
- **不统计订阅额度。** 文档里注明一句：worker 和前台会话共用同一份订阅额度。

### E2：缓存稳定

已经被下列决定覆盖，逐条核对后没有发现漏洞：

1. 只在会话开始和压缩时注入，两次压缩之间不改上文（ADR-0015）；
2. 不用 UserPromptSubmit 注入，也不改系统提示；
3. fork worker 复用主会话的缓存（D-c：读取约 19 万 token，新写入约 1400 token）；
4. 压缩本来就会让缓存失效；D4 还能把压缩安排在缓存已经过期的时候；
5. 恢复会话时重新注入的内容追加在历史之后，不会破坏已经缓存的前缀。

## 理由

- **token 加单价是通用的口径：** 能跨模型比较，也能和别人报告的数字对照。订阅额度的规则不公开，而且会变。
- **所需数据 transcript 里已经全有了，** 不需要额外埋点。

## 后果

- 单价表要手动维护，模型价格变了就要更新。
- 开销比算的是"假如按 API 计费会花多少"，不等于订阅下的实际感受。比如 worker 太勤，可能更早撞到额度上限，这个指标反映不出来。

## 什么情况下推翻

- 实际使用中经常因为 worker 撞到额度上限 → 加上额度相关的观察，或者降低 worker 的运行频率。
