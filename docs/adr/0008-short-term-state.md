# 0008. 短期记忆：每个项目一份"现状"，整份重写；长短期的划分与判断规则

## 背景

A7 原本的问题是："接续工作状态"要不要做，算不算记忆。讨论中暴露出更大的问题：

- **调研：** 各家分歧很大。trace-memory 把进度放进 open 知识，CC auto memory 放在 project 类，claude-mem 做成会话摘要注入；Hermes 和 Letta 明确不收，需要时去历史里检索。
- **我的习惯：** 我习惯在同一个会话里一直做下去，很少新开会话。所以重点不在"新会话接续"，而在压缩。
- **我的担心：** 阶段、进度、待办都变得很快。如果作为普通知识存进去，模型得自己想起来去找过时的那一条。阶段变化往往是隐式的（STALE 论文中最难的一类），模型很可能找不到，或者忘了去找。于是我提出：这种频繁修改的东西，固定放在一个位置，专门处理。
- **实验：** 标注了约 670 条真实消息，发现：
  - 压缩确实丢过待办、会话内的授权和项目目标；
  - 有一类之前漏掉的"带触发条件的待办"；
  - "悬而未决"其实分四种；
  - 有一条会话内的授权（"可以用有头模式"）很难判断该放短期还是长期。

## 考虑过的选项

1. **进度和待办作为普通知识，标"待定"**（trace-memory 的做法）
   - 问题：要靠模型自己找到并更新过时的条目，这正是我担心的地方。
2. **不进记忆，需要时检索**（Hermes、Letta 的做法）
   - 问题：压缩时会丢，实验里有真实案例。我习惯在同一个会话里做下去，压缩是常态。
3. **每个项目一份"现状"，固定位置、整份重写**（选这个）
   - 先例：LangMem 的"画像"（整体覆盖更新）、Letta 的记忆块、Hermes 压缩后重新注入待办、claude-mem 的 work_state。

## 决定

### 1. 短期记忆："现状"

每个项目一份：

| | 规则 |
|---|---|
| **存什么** | 阶段、进度、待办（**条件按原话写**）、待核实 / 待调查的事、**会话内的授权和临时指令**。每项带"截至某日" |
| **大小** | 有上限，逼着它只保留"现在" |
| **怎么更新** | **整份重写，不追加**。旧版本保留，可以查 |
| **什么时候重写** | 压缩前、会话结束时，不需要我说"阶段变了"才触发 |
| **重写规则** | 上一版的**每一项都要有交代**：完成了、还在进行、放弃了（写原因），或者**升级为长期**。不允许一项悄悄消失 |
| **怎么用** | 始终注入，压缩时一定带上 |

### 2. 长短期的划分：按"怎么更新"，而不是"活多久"

| 层 | 更新方式 | 存什么 |
|---|---|---|
| 发生了什么 | 只追加 | 原文和摘要；可以检索，帮模型和我回忆"…来着？" |
| **短期：现状** | 一份快照，整份重写 | 见上 |
| **长期：关于我** | 逐条，归档 + 替换，留版本 | 沟通方式、做事方式、审美、自动化偏好、风险偏好、背景和处境、模型犯过的错 |
| **长期：项目** | 同上 | **定位和目标（原话）**、硬约束和权限、设计决定（理解 + 指针）、**暂缓的方向**、环境事实 |

### 3. "悬而未决"分四种

| 类型 | 例子 | 放哪 |
|---|---|---|
| 当场的小决策 | "选 A 还是 B" | 不记，在上下文里几分钟就定了 |
| **暂缓的方向** | "多语言支持：不完全否决，暂时不加入" | **长期**，标"待定"，写明理由，免得以后被重新提出 |
| 待核实 / 待调查 | "某个字段的含义还没核实" | 短期（现状里的待办） |
| 有条件的待办 | "转区等有日文原版游戏再测" | 短期（待办 + 条件原话） |

这**细化了 ADR-0006**：长期知识上的"待定"标记，只用于"暂缓的方向"和还没定的设计问题；待核实和有条件的待办改放进现状。

### 4. 拿不准放短期还是长期时

1. **先看原话指向哪里：** "以后""如果再遇到""每次"放长期；"这次""现在先""可以 push 了"放短期。
2. **原话看不出来，就看是放宽还是收紧：**
   - 放宽的（授权、"可以做 X"）放短期，因为过期的授权比再说一遍危险；
   - 收紧的（"不要""别碰""小心"）放长期，多留一条禁令，最多多问一句。
3. **现状是暂存区，可以升级：** 我在之后的会话里重述了某条短期内容，就说明当初放错了，直接升为长期。升级也不扩大范围（ADR-0004）。

## 理由

- **整份重写，解决了"找不到过时条目"的问题。** 过时的东西就摆在眼前，不需要谁想起来去找。STALE 已经证明，模型很难自己察觉隐式的过期。
- **按"怎么更新"划分最清楚。** 我最初觉得阶段、进度、待办的生命周期是一个量级；但实验发现，项目阶段也可能持续几个月（比如 Lute 的"暂停维护"）。真正区分它们的是更新方式：快照还是逐条。阶段放在现状里，即使持续几个月，也只是一份快照里长期不变的一行。
- **"每一项都要有交代"，防止东西悄悄丢失。** 这借鉴了 trace-memory 的 Dreamer："每个冻结的条目都必须给出处置"。
- **会话内的授权放进现状，有真实数据支持。** 实验中压缩后丢了"可以用有头模式"，我只好问"我不是说过吗？"
- **条件按原话写，也有真实数据支持。** 实验中"新来源搞定后一口气上线"被误解成"现在就上线"。
- **判断规则利用了两边代价不对称。** 拿真实数据验证过：
  - "不能碰代理服务"（收紧 → 长期；我隔 5 天又说了一遍）；
  - "root 要用时找我授权"（收紧 → 长期）；
  - "可以 push"（放宽且指向当下 → 短期）；
  - "如果后面出现……可以用有头模式"（指向以后 → 长期）。
- **"可升级"让判错可以自我纠正，** 代价最多是我再说一遍，而这正是成功标准里要压低的对齐成本，可以统计。

## 后果

好的方面：
- 压缩时一定带上现状，D3 的三个真实案例都能覆盖。
- 和项目文档的关系清楚了：项目已经有进度文档的（比如这个项目的 `log.md`），现状只写几行加指针（ADR-0003）。
- "升级为长期"的次数，可以作为评测指标：衡量判断规则准不准。

要付出的代价和风险：
- **每次重写都要调一次模型。** 要和差异点 3（低成本）一起在 B 段权衡；现状很小，单次成本应该不高。
- **"每一项都要有交代"依赖模型照做。** 需要用校验来兜底，比如对比前后两版的条目，B 段设计。
- **现状是按项目划分的。** 我同时开多个项目，每个项目一份，互不干扰；但"我手上同时有哪些项目"这件事本身没有地方放。目前不需要，暂不处理。
- **判断规则的第一步依赖识别原话的指向，** 中文的说法很多，要在 B9 用真实数据校准。

## 什么情况下推翻

- 现状的重写经常丢项或写错，校验也兜不住 → 改为逐条维护，或者减少现状里的内容。
- "升级为长期"非常频繁 → 说明判断规则偏向短期，需要调整。
- 我开始经常新开会话 → 重新评估现状在新会话里的注入方式（C1）。
