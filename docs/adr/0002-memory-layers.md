# 0002. 记忆分两层：发生了什么、先验知识

- 状态：采纳（2026-10-22）；稳定性的地位被 [ADR-0006](0006-lifecycle.md) 修订：从"轴"降为"待定"标记；第一版简化见 [ADR-0011](0011-v1-scope-cuts.md)：作用域只留 project / global，会话级内容放进现状
- 日期：2026-10-22
- 相关：[questions.md](../questions.md) A1 · [research/a1-trace-memory.md](../research/a1-trace-memory.md) · [research/a1-landscape.md](../research/a1-landscape.md) · [positioning.md](../positioning.md)（愿景里的三类记忆）

## 背景

愿景里把记忆分成三类：共同经历、做事习惯、对我的了解。老 spec 分成两层：情景和语义。在定写入、注入、压缩之前，要先定下记忆分几类，因为这是后面所有设计的地基。

讨论中，我提出了自己的粗分：
- **发生了什么**：作用于当前会话或项目，压缩时需要。
- **先验知识**：作用于会话、项目或跨项目，这才是记忆。

我还认为，"项目事实"和"共同经历"可以是同一样东西。

随后调研了 trace-memory 的源码和提交历史，以及其他 8 个项目：Magic Context、Hermes、Letta Code、Pi OM、claude-mem、mem0、LangMem、Graphiti。

## 考虑过的选项

1. **按愿景分三类：共同经历、做事习惯、对我的了解**
   - 问题：三类不是同一个维度。"共同经历"说的是来源，"做事习惯"和"对我的了解"说的是内容。用户的一条偏好，既可以算习惯，也可以算对我的了解。
2. **四类：共同经历、关于我、规矩、项目事实**（Claude 最初的提议）
   - 让类别决定写入规则和过期方式。
   - 问题：把"项目事实"和"共同经历"拆开了，其实两者都是"发生了什么"。而"让类别决定规则"这条路，trace-memory 和 Magic Context 都走过，后来都删减了类别。
3. **照搬 CC auto memory 的四类：user / feedback / project / reference**
   - 问题：只有先验知识，没有"发生了什么"这一层。进行中的工作状态也混在 project 类里。
4. **两层 + 两个轴**（选这个）

## 决定

**第一层：两层**

| 层 | 是什么 | 作用于 | 怎么用 |
|---|---|---|---|
| **发生了什么** | 原始对话（不修改）+ 按话题切出来的情景片段 | 主要作用于当前会话 | 压缩时放进去；长期保存，跨会话可以检索，但**不注入** |
| **先验知识** | 从发生的事里留下来、会影响将来的东西 | 会话 / 项目 / 跨项目 | 跨会话注入 |

**先验知识的两个轴**
- **作用域**：session / project / global，决定在哪里成立、在哪里生效。
- **稳定性**：待定还是已确立。待定的东西变化快，要写明还缺什么才能定下来。

**类别只做标签**，用于展示和筛选。类别不决定写不写，不决定生命周期，也不作为拆分的理由。具体用哪几个标签，到实现时再定。trace-memory 的 5 个标签是一个现成的起点：约束、理解、目标、待定、参考。

**这次刻意不定的：**
- 用户要不要单列一类（Magic Context、Hermes、Letta 都单列了）→ 放到 A3/A4。
- 按加载时机分（常驻 / 按需 / 检索），以及程序性知识要不要写成 CC skill → 放到 C1。
- 记忆里要不要写来源（trace-memory 写，Letta 明确不写）→ 放到 A3。
- 接续工作状态放在哪一层 → 放到 A7。

## 理由

- **两层是共识。** 9 个项目里，有 6 家明确这样分：trace-memory、Magic Context、Letta Code、Pi OM、Graphiti、Hermes。Magic Context 的提示词直接叫它 world / experience split："它描述的是项目**是**什么样，还是**发生**了什么？"例外有三个，各有原因：
  - claude-mem 只记经历。
  - mem0 按问答基准优化，把两层摊平了。
  - CC auto memory 只有知识，经历只留在 transcript 里。
- **两层的职责不同，不是同一内容的长版和短版。**
  - "发生了什么"要忠实、完整、可追溯，是先验知识的证据来源。
  - 先验知识要能脱离原讨论被看懂，并且能直接影响行为。
- **作用域和稳定性才真正决定行为差异：**
  - 作用域决定谁能看到、预算算在哪里。
  - 稳定性决定多快会变，以及怎么整理。
- **类别只做标签，是吸取别人的教训。**
  - trace-memory 的 knowledge 从 7 类带准入条件，改成 5 类纯标签；fact 的 6 个类别全部取消。
  - Magic Context 的项目记忆从 9 类减到 5 类。
- **待定的问题都不改变"记忆是什么"，只改变"怎么写""什么时候用"，** 所以放到对应的问题里定，不塞进 A1。

## 后果

好的方面：
- 和压缩的关系清楚了：压缩主要用"发生了什么"，再带上先验知识。
- 愿景里的三类记忆都有落脚处：
  - 共同经历 → "发生了什么"，加上从中留下来的理解。
  - 做事习惯、对我的了解 → 先验知识，作用域多半是 global 或 project。
- 后面的 A2（写入标准）有了明确的对象：判断的是"什么可以从发生了什么升级成先验知识"。

要付出的代价和风险：
- **"发生了什么"要长期保存，** 存储量会一直增长。保留多久、怎么检索，要在 B、F 段处理。
- **只用两个轴，类别又是标签，** 那么"哪些记忆能用 hook 强制执行"就不能靠类别来判断，需要在 C3 另找判据。
- **用户单列的问题被推迟了。** 如果 A3/A4 决定单列，可能要在这份 ADR 的基础上补一条维度，但不会推翻两层结构。

## 什么情况下推翻

- 实验或使用中发现，"发生了什么"跨会话**必须注入**才有用（比如接续工作离不开它），而不只是检索 → 重新考虑两层的边界。
- 发现两个轴不够用，必须靠类别来驱动写入或生命周期，才能做好某件事（比如 hook 强制执行）→ 新写一份 ADR，补上类别的职责。
