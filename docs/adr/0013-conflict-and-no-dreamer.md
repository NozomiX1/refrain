# 0013. 冲突与整理：长期知识设硬上限，worker 每次读入全部并四选一裁决；第一版不做 Dreamer

## 背景

ADR-0006 已经定了在写入时裁决冲突，B5 只剩一个问题：worker 怎么找到相关的旧条目。B6 原本打算设一个单独的整理角色（Dreamer），负责合并、去重、清理过时内容、控制预算，还有提醒项目文档该更新。

我们按 ADR-0011 的标准重新审视：一个机制，要么有真实案例支撑，要么推迟。

Claude 的方案依赖一个前提：长期知识很短，worker 可以一次读完。我要求先确认这个前提。量下来的结果是：

- **现有的 auto memory：** 另一个项目约 3.8k token，本项目约 2.1k，第三个项目约 0.7k，都只用了两天左右。
- **按标注实验粗估：** 关于我的有 15–30 条，每个项目 20–40 条，每条 60–100 token，合计约 3k–6k token。

现在确实很短，但样本只有两周。几个月以后，跨项目的知识会越积越多。所以"短"不能当前提，要当规则。

## 考虑过的选项

**B5：worker 怎么看到旧条目**
1. 按相关性检索，比如向量检索，或者 mem0 的做法。
2. **每次读入全部长期知识，靠硬上限保证读得下**（选这个）。

**B6：要不要 Dreamer**
1. 设单独的 Dreamer，像 trace-memory、Magic Context、Letta 那样。
2. **第一版不做，它的职责都由 worker 在写入时完成**（选这个）。

## 决定

**1. 长期知识设硬上限。** 初始值参照 trace-memory：全局 4k token，每个项目 15k token，实验时再调。超出上限时，worker 必须在同一次运行里合并或归档，腾出空间（Hermes 的做法）。

**2. worker 每次运行都读入全部相关的长期知识，**也就是当前项目的加上全局的，不做检索。

**3. 对每条候选内容，四选一：**
- **新建**
- **更新某条**：旧版本归档
- **归档某条**：写明原因
- **不写**

不允许新旧两条都留着（ADR-0006）。

**4. 第一版不做 Dreamer。** 原来设想的职责，分别这样处理：

| 职责 | 怎么处理 |
|---|---|
| 合并、去重 | 写入时处理。worker 能看到全部知识 |
| 清理过时内容 | 写入时裁决 |
| 超出预算 | worker 在同一次运行里合并或归档 |
| **提醒项目文档该更新** | 在 worker 的提示词里加一条：发现对话中的新决定和某份仓库文档对不上，就在现状里加一条待办"更新某文档" |

## 理由

- **读全部比检索简单，而且不会漏。** 检索可能漏掉相关的旧条目，而漏掉旧条目，正是 STALE 论文说的"新旧两条都留着"。有了上限，worker 每次读入的量不超过 2 万 token，用 Haiku 的话几乎不花钱。
- **上限本来就躲不掉。** 长期知识每次开会话都要注入，必须控制大小。CC 的 SessionStart 注入有字符上限，这一点在 C1 处理。
- **Dreamer 的职责，写入时都能做。** 前提是 worker 能看到全部知识。
- **"提醒文档该更新"有 3 个真实案例。** 但它只需要提示词里的一句话，不需要单独的角色。

## 后果

好的方面：
- 第一版少了一个角色，也少了它的触发逻辑和预算调度。
- 不需要检索设施。

要付出的代价和风险：
- **一次调用里同时做提取和裁决，可能两件事都做不好。** mem0 发现这样做效果不好，最后干脆放弃了写入时对账；trace-memory 也是把 Noter 和 Dreamer 拆开的。这个风险并入 E7 实测。
- **上限可能把有用的知识挤掉。**
- **提醒文档更新可能变成噪音。** 如果 worker 经常误报"文档对不上"，这条规则就得改。

## 什么情况下推翻

- **E7 发现一次调用做不好两件事**（漏提取或者裁决出错）→ 拆出单独的 Dreamer，以 trace-memory 为样板：Noter 只管提取，Dreamer 只管整理。
- **上限挤掉了有用的知识** → 提高上限，同时 worker 改为检索相关条目，不再全部读入。
- **"文档该更新"的待办大多是误报** → 删掉这条提示词规则。
