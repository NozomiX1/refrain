# 0015. 上下文拼装：压缩和恢复会话是"接着做"，新会话是"有选择地忘记"

- 状态：采纳（2026-10-23）；切片注入已经实测可行，但**顺序不固定**（hook 并行执行），每一片必须能单独读懂（[research/d-experiments.md](../research/d-experiments.md) D-a）；恢复会话的处理被 [design.md](../design.md) 4.5 修订：缓存还在就原样恢复、不追加，缓存过期就换成交接；**切片注入被取代**：改用 mod 的 `prompt.context` 自定义块，引擎在新会话、`/clear`、每次压缩之后各发一份，恢复会话时不重发，实测 10 万字符完整（D-a3，design.md 4.1）；`classic.SessionStart`（D-a2）作为退路。压缩时交接不再放知识和项目现状，由简报块自动带上（design.md 4.4）；压缩时摘要的 10k 预算被 design.md 4.3 / 4.4 的统一折叠规则（N、K、标题上限）取代，会话现状改放进简报块；**注入方式再次被取代**（2026-10-26）：`prompt.context` 会发给每个子 agent（书记员也收到了主模型的简报），改用 `classic.SessionStart` 的 `additionalContext`，只给主会话，恢复和 fork 时跳过（design.md 4.1、e2，过程见 evolution.md）

## 背景

C1 问的是什么时候注入、怎么注入，C2 问的是冻结快照还是即时生效。讨论中有四次修正：

1. **Claude 曾建议把项目知识的上限降到 1 万字符，以迁就 SessionStart 的字符上限。** 查了 trace-memory 以后，这个建议收回了。trace-memory 用 24 个 hook 切片绕过上限，还把项目预算从 10k 调高到 15k token，说明 10k 不够用。
2. **我指出：压缩之后，上文里必须有"发生了什么"。** 而且一个长会话会压缩很多次，摘要会越积越多，所以压缩时也要逐出。
3. **我追问：压缩如果不失真，新会话还有什么价值？它和压缩为什么不同？**
   - 如果只是想接着做，应该恢复原会话（`--continue`），CC 本身就支持。
   - 主动开新会话，本身就是一个信号：前面的过程不要了，只带上真正长期有用的东西。比如换了任务，或者想甩掉走错路时留下的假设。
   - 所以，新会话的价值在于**有选择地忘记**。
4. **我指出：摘要应该属于项目、在项目内共享，**这样才能快速定位做过什么。"不放进上文"不等于查不到。

## 决定

### 1. 两种入口

| | **接着做**：压缩、恢复会话、fork | **重新开始**：新会话、`/clear` |
|---|---|---|
| 长期知识 | ✓ | ✓ |
| 现状的**项目级**部分：阶段、进度、待办、待核实 | ✓ | ✓ |
| 现状的**会话级**部分：授权、临时指令 | ✓ | **✗** |
| 本会话的摘要 | 压缩时按预算放入（见第 2 条）；恢复会话和 fork 时，CC 自己就带着历史 | — |
| 同项目其他会话的摘要 | 不放进上文，需要时检索（C6） | 不放进上文，需要时检索（C6） |
| 还没处理的原文尾巴 | 压缩时原样保留 | — |

压缩时**只放本会话的摘要**。其他会话的摘要，在开这个会话时就有意没有带进来，压缩时也不应该再塞进去。压缩的任务是保真，不是往里加东西。

**摘要属于项目，不属于会话。**做过什么是项目层面的事，所以同一个项目里所有会话的摘要放在一处，按时间排列，并标明来自哪个会话（类似本项目的 `docs/log.md`）。检索时以整个项目为范围；压缩时按会话标记，挑出本会话的那部分。

### 2. 压缩时摘要的逐出

摘要按时间倒序放：最新的放全文；放不下的，只留一行标题；标题也放不下的，就逐出。

- 逐出的摘要连同原文都还在磁盘上，可以检索回来。
- 留标题，是为了让模型知道"这件事做过"，从而知道该去检索。
- 预算初始值参照 trace-memory，设为 10k token。全文和标题各占多少，交给 E6 来定。

### 3. 现状分成两部分（修订 ADR-0008）

- **项目级**：阶段、进度、待办（条件按原话写）、待核实。跨会话保留。
- **会话级**：授权、临时指令。只在本会话内有效，新会话不带。

### 4. 两次压缩之间不注入（C2：冻结快照）

会话中途写进去的新知识，本来就是从这个会话里提取出来的，原文还在上下文里，不需要再注入一遍。只有一种例外：我同时开着的另一个会话写进了全局知识。这种情况等到下次压缩或者开新会话时再看到。注入只发生在会话开头，缓存保持稳定。

### 5. 注入的方式

- **长期知识的预算不变**，仍按 ADR-0013：全局 4k、项目 15k token。
- **切片注入**：固定注册 8 个 SessionStart hook，第 i 个只输出第 i 片，每片不超过 1 万字符。19k token 即使全是英文，也只有约 7.6 万字符。
- **快照文件**：worker 每次写完，把要注入的内容渲染成快照文件，用原子替换写入。hook 只负责读取和切片，不做计算，所以不会拿到不一致的版本。
- **用陈述事实的写法**，不写成命令。官方文档说，命令式的写法可能触发提示注入防御。
- **压缩的两条路（取决于 D2）：**
  - 能接管 CC 的压缩：拼装好的压缩内容里已经包含全部内容，压缩后的 SessionStart 不再注入。
  - 接管不了：用 CC 自己的总结，再由压缩后的 SessionStart 注入长期知识和完整的现状。

### 6. 修订 ADR-0010 第 4 条

"摘要跨会话不主动注入"仍然成立：新会话不带以前会话的摘要。但压缩时，本会话的摘要按第 2 条放入。

### 第一版不做

子 agent 的注入、UserPromptSubmit 注入、MCP instructions、"按需加载"这一档、把程序性知识做成 skill。这些都没有真实案例支撑。

## 理由

- **新会话和压缩的区别，来自目的不同。** 一个是接着做，一个是重新开始，不是随意定的。
- **会话级授权不能带进新会话。** ADR-0008 说过，"过期的授权比再说一遍危险"。ADR-0011 删掉 session 作用域以后，授权都放进了现状。不把现状分成两部分，新会话就会带上旧授权。
- **切片有先例。** trace-memory 用 24 个 hook 在实际使用中验证过；官方文档也写明，每个 hook 的输出单独计算上限。
- **按时间倒序逐出、保留标题，是最简单的做法，而且不丢东西。** 原文和摘要都还在。标题可以缓解"模型不知道有这回事，所以不会去检索"的问题。
- **冻结快照**：trace-memory 也放弃了持续的前台更新，改为初始注入。

## 后果

好的方面：
- 新会话真正能用来重新开始。
- 一个会话跑十几天、压缩很多次，上文也不会被摘要撑满。
- 缓存稳定。

要付出的代价和风险：
- **新会话里要重新给授权。** 这是有意为之。
- **worker 写现状时，要分清哪些是项目级、哪些是会话级。** 这是又一个要写进提示词的边界，在 B9 里一起校准。
- **8 个 hook 按顺序拼接，依赖 CC 的行为。** 要在 D1 实测。
- **按时间倒序逐出，可能把很早但重要的事挤成一行标题。** 重要的东西应该已经升级成长期知识了；如果实测发现经常不是这样，再考虑按重要性排序。

## 什么情况下推翻

- 我开始经常为了接着做而开新会话，而不是用恢复会话 → 新会话也按预算带上以前会话的摘要。
- E6 发现按时间倒序放摘要，压缩后经常接不上 → 改用分层压缩（Magic Context、Pi OM 的做法），或者按重要性排序。
- D1 发现多个 hook 的输出没有按顺序拼接，或者被截断 → 换注入通道，或者缩小预算。
