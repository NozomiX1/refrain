## 愿景

今天的 LLM 本质上仍是一台预测下一个 token 的机器：给它上文，它续写下文。模型本身不带任何记忆。这是优点，因为它干净、可控；也是缺点，因为每次都从零开始。当我们希望它成为一个"人"、一个助手时，替它维护上文就成了一件繁重的工作。

对人来说，记忆几乎是最重要的东西：我们经历过什么、学到了什么，决定了我们将来会怎么做。所以给 LLM 加上记忆，既非常有价值，也非常难。我认为这是让模型更接近智能的一个好方向。

我希望 Claude Code 能有长期记忆，具体包括三样东西：

- **我们一起做过什么**：共同的经历。
- **我们形成了怎样的做事习惯**：在合作中沉淀下来的默认做法和决策方式。
- **我是一个什么样的人**：我的偏好、习惯和思考方式。

有了这些，它才能成为一个长期共事的伙伴。理想的状态是一种默契：我随口说几句，它就明白我要什么，然后把它做出来。

Claude Code 是"人"，游戏里的 NPC 是"人"，将来每个人的 AI 助手也是"人"。让它们拥有记忆，是这个项目的终极目标。这个插件是第一步。三者共通的是对"记忆之于一个智能体意味着什么"的理解，实现不必统一。

**愿景怎样落到这一版：** 默契是可以测量的。共享的背景越多，表达意图需要说的话就越少，所以"为了让对方理解你所付出的成本"会下降。这就是成功标准里的"用户纠正次数下降"。愿景是北极星，用来判断方向；这一版的范围由下面的定位决定。

## 一句话

一个给 Claude Code 用的跨会话记忆系统：**让模型越用越懂我，而记忆系统本身的消耗不超过它省下的。**

## 要解决的问题

来自我自己的日常使用：

1. **跨会话、跨项目的遗忘。** md 文档也能记，但一多就整理不过来。
2. **对齐成本。** 每次都要重新解释我想要什么、我的习惯是什么。
3. **压缩丢信息。** 压缩一旦丢掉关键信息，后面的任务就会出错。
4. **成本。** 总结一个会话可能和这个会话本身一样贵，再加上整理，订阅额度扛不住。
5. **记忆的影响看不见。** 模型行为反常时，不知道是不是某条记忆在起作用。事后能查看、能修正还不够，要能看到这一次用了哪些记忆。（2026-10-22 新增）

1–3 和 5 是**要交付的价值**，都要解决。1–3 按上面的顺序排优先级，5 的优先级待定。4 是**约束**：记忆系统消耗的额度必须远小于它带来的价值。成本不是一个"功能"，而是对每个设计的否决条件：方案再好，成本太高也不采用。（2026-10-22 确认）

## 用户

- **第一用户：我自己。** CC 订阅用户（不用 API），重度 vibe coding，同时开多个项目，中英混合交流。
- **第二用户：和我类似的 CC 订阅用户。** 将来会服务，现在先做好自己用的。设计上不要把路堵死，但安装体验和适配别人的习惯不是现在的优先级。

## 目标

- 跨会话和跨项目都能记住，并且自动整理，不需要我手动维护。
- 记住我的偏好和纠正过的地方，减少重复说明。
- 压缩之后，任务能接着做对。
- 每条记忆能追到来源，我能查看和修正。错误的记忆比没有记忆更糟。
- 能看到模型这一次用了哪些记忆。

**什么算记忆：** 会影响将来的东西，比如我的习惯和偏好、模型犯过的错、项目里定下的约定。只是"发生过"、对将来没有影响的事情，不算记忆。

## 非目标

- 不支持其他宿主（Pi、Cursor 等）。
- 不做团队或多人共享的记忆。
- 不做游戏适配。游戏可以借鉴这里的设计，但不必统一（见 [archive/ai-native-game.md](archive/ai-native-game.md)）。
- 不做通用的记忆服务或 SaaS。
- 不替代手写的 CLAUDE.md，两者共存：CLAUDE.md 放明确的规则，记忆系统放从对话中学到的东西。

## 约束

- **只用 CC 订阅额度**，后台 worker 和前台会话共用这份配额。
- **CC 的扩展点是固定的**：hooks、插件、MCP，以及可能存在的实验性 API。具体能力和限制要实测，旧 spec 的 §5.2 是 2026-10 查的文档。
- **一个人开发，时间有限**，只做必要的实验。

## 差异化（2026-10-22 横向扫描后确认）

证据见 [research/scan.md](research/scan.md)。

1. **忠实且被遵从的用户模型。** 别家都有用户画像，但画像会编造内容（研究称约四成超出证据），记住了也不一定照做（用 Mem0 时，57.5% 适用的偏好仍被违反）。我们要求每条都链接到我本人的证据，并标明是原话还是推断（推断只作假设，见 [ADR-0004](adr/0004-evidence-and-hypotheses.md)）；能强制执行的，就用 hook 强制执行，而不只是提醒。
2. **使用归因。** 已经有方案能显示"注入了哪些记忆"，但没人告诉用户"这一次实际用了哪条"。这是最难的一点，可行性要靠实验验证。
3. **可量化的低成本。** 降成本的手段已有共识，但在 CC 的真实使用中，没人报告记忆开销比。我们要报告这个数字。
4. **冷启动。** CC 场景下没人回填历史 transcript。

不是差异点、但要做好的：压缩时不调模型、只渲染（Pi 生态的共识）；缓存稳定。

**最初的假设和验证结果**（保留作为历史）：

| # | 最初的假设 | 结果 |
|---|---|---|
| H1 | 现有的 CC 记忆方案，额外消耗都很高 | 改写为"CC 真实使用中没人报告记忆开销比" → 差异点 3 |
| H2 | 现有方案没有认真建模用户本人 | **推翻**。改写为"没人保证用户模型忠实和被遵从" → 差异点 1 |
| H3 | 现有方案不会利用已有的 transcript | 成立 → 差异点 4 |
| H4 | CC 内置 auto memory 有具体的不足 | 成立：只按仓库隔离、靠主模型想起来才写、没有整理、没有来源 |
| H5 | 现有方案都不告诉用户这一次用了哪些记忆 | 改写为"没人做使用归因" → 差异点 2 |

## 讨论过、暂不纳入的

- **接续工作状态**（上次做到哪、还剩什么、卡在哪）：确实是痛点，但还没想好怎么做，先放进问题清单。
- **给子 Agent 喂记忆**：这是 Claude 提的，不是我的痛点，先不考虑。
- **以纠正为中心作为项目特点**：太窄了。纠正只是会影响将来的东西中的一种，习惯、偏好、约定同样重要。"纠正不能一次生效"本来就是记忆插件该解决的，不需要单独作为特点。

## 成功标准

- **定性：** 我自己每天开着它，关掉会觉得难受。
- **定量**（要能和基线对比、别人能重跑，具体数字测出来再填；测法见 design.md 第 8 章）：
  - 压缩后关键事实的保留率：refrain vs CC 原生压缩 vs 不压缩
  - 新会话接续准确率：无记忆 / auto memory / 只存原文加检索 / refrain / 全量历史，在约 1、3、6 周各测一次
  - 编造率：知识里找不到依据的比例
  - 记忆开销比（书记员的花费 ÷ 主会话的花费）
  - 对齐成本：真实使用前后，每 100 条我的消息里的纠正次数
  - 负迁移（因为记忆反而做错）足够少
