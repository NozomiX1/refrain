# 0006. 生命周期：作用域区分临时与长期，"谁说了算谁推翻"，稳定性降为"待定"标记

- 状态：采纳（2026-10-22）；"待定"标记的适用范围被 [ADR-0008](0008-short-term-state.md) 细化：只用于暂缓的方向和未定的设计问题；第一版简化见 [ADR-0011](0011-v1-scope-cuts.md)：去掉 session 作用域、"在世界"知识的自动核验和推断的作废期限
- 日期：2026-10-22
- 相关：[questions.md](../questions.md) A5 · [research/a5-lifecycle.md](../research/a5-lifecycle.md) · **修订 [ADR-0002](0002-memory-layers.md) 中稳定性的地位** · [ADR-0004](0004-evidence-and-hypotheses.md)（原话与推断）· [ADR-0005](0005-user-model.md)（"关于我"标记）

## 背景

老 spec 提出了两个问题：
- §7.4："这次先别写测试"是临时指令，不应该覆盖"我习惯写测试"这个长期偏好。
- §7.3：项目决策在代码变更后可能不再成立。

ADR-0002 把先验知识组织成两个轴：作用域和稳定性。讨论 A5 时我追问"稳定性到底起什么作用"，结论是它不需要成为一个轴。

调研了 STALE 论文全文，以及 trace-memory、Magic Context、Graphiti、mem0、Hermes、Letta、CC auto memory 的过期处理；还查了 trace-memory 的源码和提交历史，看它的 `open` 类别是怎么演变的。

## 考虑过的选项

**临时指令和长期偏好**
1. 单独设计一套生命周期，比如"临时指令"类型，加过期时间。
2. **用作用域区分**（选这个）。

**过期的判定**
1. 按时间过期，比如按类别设 TTL（Magic Context 的旧做法，现行版本已放弃）。
2. 什么都靠代码核验（老 spec §7.3 的想法）。
3. **按"真相在哪"决定谁能推翻，在写入时裁决**（选这个）。

**稳定性**
1. 保持为轴（ADR-0002 原来的写法）。
2. **降为标记**（选这个）。

## 决定

**1. 临时指令和长期偏好，用作用域区分。**
"这次先别写测试"按 ADR-0004 的"不扩大范围"，作用域就是 session。在它的范围内，**窄作用域的覆盖宽作用域的**，但不会改写那条长期偏好。

**2. 谁能推翻一条知识，看它的真相在哪：**

| 真相在哪 | 例子 | 谁能推翻 | 怎么发现失效 |
|---|---|---|---|
| **在我** | 偏好、裁决、"关于我"的知识、我做的项目决定 | 只有我的原话 | 我自己说；或者发现冲突时问我（C5） |
| **在世界** | 代码事实、环境、外部系统的限制 | 新的观察 | 把知识关联到具体的文件和版本，有变化时重新核验 |

真相在我的知识，和代码对不上时，**不自动推翻，而是标出冲突、问我**。因为写错的也可能是代码。

**3. 隐式冲突在写入时裁决。** 新证据进来时，检查受影响的旧知识，包括连带失效的，当场判定为保留、过期、替换或不确定。不能把新旧两条都留着，让读的模型自己去选。具体机制在 B5/B6 设计。

**4. 失效就归档，不删除。** 归档时写明原因：不再成立，还是只是放不下。历史保留可查。

**5. 时间：** 已确立的知识**不因时间过期**。所有知识注入时都带"截至某日"，让模型和我能看出它放了多久。推断出的假设，一段时间内没有新证据就作废，具体多久留给实验去定。

**6. 修订 ADR-0002：稳定性从"轴"降为"待定"标记。**
- 作用域是唯一的轴，它决定知识在哪里成立、谁能看到、预算算在哪里，这是结构性的。
- "待定"和"关于我"（ADR-0005）、"原话 / 推断"（ADR-0004）一样，是挂在知识上的标记。
- 一条先验知识 = 正文 + 作用域 + 标记 + 类别标签。

**"待定"标记附带的规则：**
- 正文写明当前状态、还没解决的部分，以及需要什么才能定下来：证据、谁来裁决、完成条件。不要为了凑格式编一个缺口出来。
- **已确立的知识不退回待定。** 对它的质疑或替代方案，单独记一条待定知识；原来那条在被推翻之前继续有效。关于同一个对象的一条待定知识和一条已确立知识，不算重复。（来自 trace-memory 2026-09-19 的版本）
- 主要靠新证据来更新：解决了，就在原编号上去掉"待定"；不再相关，就归档。

**这次不定的：**
- "待定"的边界怎么判，新增为 B9。
- 待办要不要进记忆：A7。
- 定期整理怎么做：B6。

## 理由

- **作用域已经能表达"临时"。** 不需要再设计一套生命周期，ADR-0004 的"不扩大范围"会自然产出 session 作用域。
- **"谁说了算谁推翻"，和 ADR-0004 是同一个道理。** Magic Context 也不允许代码核验去推翻流程规则，"因为它们的真相在团队的行为里，不在代码里"。
- **必须在写入时裁决。** STALE：最好的模型总分只有 55.2%；问题里预设了旧状态时，连带失效的情况下最多只有 14%；"能看到不等于有权威"，新旧都检索到了照样答错。写入时裁决（CUPMem）把总分从 8.7% 提到 68.0%。
- **归档而不删除**，是 trace-memory、Graphiti、mem0、CUPMem 的共同做法，也和我们 ADR 只追加不改写的思路一致。
- **按时间过期，这个信号太弱。** Magic Context 现行的类别不再设 TTL；mem0 把时间只当作软排序。"截至某日"把时间信息交给读的人，不让系统替他做判断。
- **稳定性降为标记：** 它只影响知识怎么写、怎么读，外加一条维护规则，这些一个标记就够了。trace-memory 最后也把 `open` 做成了标签。如果以后需要按稳定性来调度整理，再升回轴。

## 后果

好的方面：
- 结构更简单了：只有一个轴，再加几个标记。
- 临时指令不需要专门的机制。

要付出的代价和风险：
- **写入时裁决要花钱。** CUPMem 每个实例约 $0.37，LightMem 约 $0.02。这要和差异点 3（低成本）一起权衡，在 B 段设计。
- **真相在我的知识和代码冲突时要问我，** 问多了会烦，和 C5 一起设计。
- **"在我"和"在世界"的边界会模糊。** 比如"我决定用 SQLite"是我的决定，"项目现在用 SQLite"是世界的事实。写入时要分清，这个判断交给 B9 一并处理。
- **没有定期回看，没人再碰的待定知识会一直留着，** 直到被预算挤出去。"截至某日"只能缓解，不能根治。

## 什么情况下推翻

- 发现"截至某日"不够用，旧的待定知识持续误导模型 → 在 B6 加上定期回看，或者把稳定性升回轴。
- 发现窄作用域覆盖宽作用域，在实际使用中经常不符合预期 → 重新设计临时指令的处理方式。
