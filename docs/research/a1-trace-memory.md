# A1 调研：trace-memory 怎么给记忆分类

> 目的：回答 A1"记忆分几类"。重点看 trace-memory 分了哪些层、为什么这样分、分类改过几次。
> 日期：2026-10-22
> 证据等级：**S** = 源码、提示词、提交记录（commit `5f96364`，2026-10-11）。读的是 `CONTEXT.md`、`src/core/prompts/`、`docs/`、`plugin/README.md` 和 git log。

## 1. 三层，各管各的

| 层 | 是什么 | 谁写 | 属于谁 | 怎么用 |
|---|---|---|---|---|
| **Raw** | 宿主记录的原始对话：用户消息、工具调用和结果、助手回复 | 系统记录，不改 | 会话 | 唯一的事实来源。压缩时放最近、还没提取过的部分 |
| **Fact** | 一个话题在一段连续对话里的切片，"还原当时的情景，而不是一条脱离上下文的结论"。可以跨多个 Turn | Noter（后台） | 会话（最早那个 Turn 所在的会话） | 压缩时放最近的；跨会话只能搜索、按地址读，**不注入** |
| **Knowledge** | 一个话题"持续的理解"："情景弱，理解强"。脱离原讨论也能看懂，并告诉读者什么时候该去查、去哪查 | Noter 新建、更新、归档；Dreamer 合并、拆分、归档 | 作用域：session / project / global | 会话开始时**只注入这一层**；压缩时也带上 |

提示词里的原话："三层职责不同，**不是同一内容的长、中、短三个版本**。证据链是 knowledge → fact → Raw。"

压缩时放进去的材料，按顺序是：fact 标题、完整的 fact、用户原话、Raw、正在运行的任务。会话开始时注入的只有 Knowledge。也就是说：

- **Raw + Fact = 发生了什么**，主要给压缩用。
- **Knowledge = 从发生的事里留下来、对将来有用的东西**，跨会话注入。

## 2. Knowledge 的三个维度

| 维度 | 取值 | 起什么作用 |
|---|---|---|
| **scope**（作用域） | `session`：只在这个会话成立，比如会话内的约束、正在等的回复<br>`project`（默认）：在这个项目成立，包括比项目窄、但要跨会话用的东西（范围写在正文里）<br>`global`：跨项目成立，比如用户的偏好、通用的环境和做事方法 | **决定谁能看到、在哪个池子里整理、预算算在哪**。预算默认 global 4k / project 15k / session 1k |
| **category**（用途） | `constraint`：以后的行动要遵守的规则、偏好、约定<br>`understanding`：对某个对象当前的理解和理由，包括机制、设计原因、教训<br>`goal`：中长期目标，不含进度<br>`open`：不稳定、变化快的东西，比如短期状态、待办、正在做的事、等回复或等裁决的问题<br>`reference`：值得以后查的对象、数值、资料，以及什么时候用、去哪找 | **只是标签**：注入时按类别分组展示。不决定写不写，不决定生命周期，不作为拆分的理由 |
| **topics**（主题） | 自由字符串，比如模块名 | 只用于分类和检索 |

两条值得注意的规定：
- **global 收得很紧。** 维护者 2026-09-20 的裁决：global 只放跨项目成立的东西；和某个项目主题相关的领域知识，包括为它查的文献和工具，都算 project。
- **没有单独的用户画像。** 用户偏好就是 `constraint` 或 `understanding`，作用域是 `global`。

## 3. 分类改过几次，以及改了什么

这是"别人如何抉择"最有价值的部分。

**Fact：从按句子打标签，改成按话题切片**（2026-09-26，ticket 92/93）
- 之前：每个 fact 是一行文本，有 6 个类别（question / proposal / decision / observation / interpretation / event）、actor、status（completed / reported / dispatched / attempted）。每个类别配一个判定问题。
- 之后：去掉 fact 级别的类别、actor 和 status。一个 fact 是一个话题的切片，每条来源各写一段摘要，角色（user / assistant / observation）由系统根据原始消息推出来。
- 我的理解：按句子分类会把情景切碎，丢掉来龙去脉；而"谁说的"本来就能从原始消息推出来，不需要模型去标。

**Knowledge：从 7 类加判定问题，改成 5 类纯标签**
- 2026-09-19（ticket 58）：分成三"种"知识，每种有不同的准入条件：
  - 已确立的决策知识（goal / constraint / mechanism），满足依据条件才能写；
  - 待定的决策知识（open / dispute）；
  - 辅助知识（term / reference），无条件写。
- 2026-09-26：合并成 5 类。mechanism、term 并入 understanding，dispute 并入 open。规则改为"**先判断值不值得留，类别只标注主要用途，不决定准入**"。
- 现在的提示词："类别没有固定的优先级"；"不要只因为类别不同就拆分"；"按稳定性和用途选类别"。
- 我的理解：给每一类定准入条件，结果过拟合、难以维护。最后统一成一个准入问题，类别退化成展示用的标签。

**现在唯一的准入问题：**
> 没有它，读者还能不能意识到相关的概念、对象、经历或问题存在，正确理解当前的看法，并恢复所需的判断或行动？

- 会妨碍意识到或接着做 → 写成 knowledge。
- 只丢细节 → 留在 fact / Raw 里。
- 没有新的理解 → 不写。
- 排序依据是"**忘了会有什么后果**"：会不会丢掉讨论的主线、误解用户、选错、重走被否决的路、漏掉未完成的事、大大增加恢复成本。

## 4. 和我们的问题直接相关的其他做法

- **接续工作状态放在 knowledge 的 `open` 里**，而不是放在 fact 里。"goal 不含进度"，进度、待办、卡点都写进 open，作用域是 session 或 project。完成后，留下的理解改类别后继续保留，或者归档。
- **证据纪律**（和 A3 有关）：
  - "用户对自己的情况、偏好和决定的陈述是权威的；**问句不是立场**。用户对外部事实的解释仍然需要证据。"
  - "提议不是决定"；"引用不会把 agent 的提议变成用户的决定"；"**重复出现只提示复查，不扩大适用范围，也不会把 agent 的要求变成用户的裁决**"。
  - 每个 knowledge 版本都要引用支撑它的 fact，fact 又引用到具体的 Raw 条目。
- **过期**（和 A5 有关）：归档分两种。`budget`：内容仍然成立，只是放不下；`invalid`：不再成立，要写明理由、证据和替代项。知识只有版本和归档，不硬删除。
- **和 CC auto memory 的关系**（和 A6 有关）：只在自己的后台 worker 里设置 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`，没有处理主会话的 auto memory，等于默认共存。

## 5. 对 A1 的启发

1. **用户提出的分法，"发生了什么" vs "先验知识"，和 trace-memory 的 Fact/Raw vs Knowledge 基本一致**，包括"前者主要给压缩用、后者才跨会话注入"这一点。
2. **真正决定行为差异的不是类别，而是两个轴：作用域（在哪里成立）和稳定性（open 还是已确立）。** trace-memory 试过让类别决定准入，后来退回去了。
3. **没有单独的用户模型**是 trace-memory 的选择。我们的差异点 1 要求"忠实且被遵从"，它在"忠实"上已经有很强的机制（引用链 + 用户陈述的权威规则），但没有"遵从"（不做强制执行）。所以差异点 1 的"遵从"一半仍然成立，"忠实"一半要承认 trace-memory 已经做了很多。
4. 待定的地方：
   - "接续工作状态"放在哪一层：trace-memory 放进 knowledge 的 open。
   - "共同经历"能不能长期保留：trace-memory 的 fact 永久保存、可以搜索，但不注入。
