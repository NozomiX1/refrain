## 背景

老 spec 第 8 节列了四个维度、十几个指标，五个对照组：无记忆、手写 CLAUDE.md、auto memory、trace-memory 和本系统。按 ADR-0011 的标准（没有真实需求就不做），第一版只保留能直接回答"成功标准有没有达到"的指标。

另外有两个现实条件：用户只有我一个人；第一版只做差异点 1 的一半（有证据、标明原话还是推断）和差异点 3（成本）。

## 决定

### 指标

| 对应什么 | 指标 | 怎么测 |
|---|---|---|
| 差异点 1：忠实 | **编造率**：记忆里找不到我原话支撑的条目所占的比例 | 每条记忆都带证据地址，用判分模型逐条对照原文检查，全自动 |
| 成功标准：纠正次数下降 | **对齐成本**：每 100 条我写的消息里，有几次是纠正或重新解释 | 把标注实验的做法自动化，比较装插件前后的 transcript |
| 成功标准：压缩后关键信息不丢 | **压缩保真率**：压缩后能不能答对压缩前的关键事实（待办、授权、目标） | 取真实的长会话，在同一个位置分别用 CC 原生压缩和我们的拼装做压缩，再用一组问题去问 |
| 差异点 3：成本 | **记忆开销比**：worker 的花费 ÷ 主会话的花费 | 从 transcript 的用量字段算，按单价加权（缓存读、缓存写、输入、输出的价格不同），细节见 E1 |
| 成功标准：负迁移少 | **负迁移次数**：因为记忆反而做错的次数 | 第一版靠我手动记录。等使用归因（C4）做出来，才可能自动统计 |

**定性标准不变：** 我自己每天开着用，关掉会觉得难受。

**第一版不测：** 遵从率（需要构造"这条记忆应该起作用"的场景）、写入召回率，以及老 spec 里其余的指标。

### 对照组和两种测法

- **离线回放（可控）：** 拿已有的 transcript 比较三组：**无记忆**（下限）、**只开 auto memory**（我现在的真实基线）、**本系统**。trace-memory 暂时不比，等到需要对外说明"和别人比怎么样"时再加。
- **纵向使用（真实，但有噪声）：** 比较装插件前后日常使用中的对齐成本。旧的 transcript 就是"只开 auto memory"时期的基线。前后做的项目不同，所以这个结果只当信号看。
- **判分：** 由判分模型打分，我人工抽样校准。

### 离线回放不算冷启动

离线回放要拿历史 transcript 跑 worker，生成"如果当时就有插件，记忆会是什么样"。这只是评测手段，不是产品功能，不违反"第一版不做冷启动"（ADR-0011）。

## 理由

- **每个指标都对应一条成功标准或一个差异点。** 没有对应的就不测。
- **编造率可以全自动测。** 每条记忆都带证据地址，这是 ADR-0004 设计的直接好处。
- **对齐成本的测法已经验证过。** 标注实验用的就是这个方法，从中找出了最常见的"关于我"、项目定位被重述了 3 次，以及压缩丢掉东西的 3 个案例。
- **只有我一个用户，不可能在真实工作里同时跑五套系统。** 所以要靠离线回放来提供可控的比较。
- **auto memory 是真实的基线。** 旧的 transcript 本身就是它的数据，不用另外构造。

## 后果

- 测量本身要花钱：判分模型、离线回放跑 worker。离线回放可以只挑少量会话来跑。
- 纵向比较的噪声很大。一个人、几周的数据，结论只能算方向性的。
- 负迁移靠手动记录，很可能漏记。

## 什么情况下推翻

- 编造率稳定很低以后 → 加上遵从率，补齐差异点 1 的另一半。
- 要对外发布或者写成文章 → 加上 trace-memory 对照组，以及更多用户。
