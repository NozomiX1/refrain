# 0018. 存储与隐私：全局 SQLite 单写者；不做独立库和主体字段；第一版不脱敏，防投毒靠来源

## 背景

F 段是实现层面的问题。

老 spec 的设想是：用 SQLite 存储；记忆核心做成一个独立的库，同时给游戏用；存储结构里从一开始就带上"主体"和"可见性"字段。

ADR-0010 和 ADR-0016 留下了一个隐私问题：原文里有我以明文发过的密码，检索原文时可能把它带进上下文。我做了一次统计，只数数量，不输出内容：在我本人写的消息里，提到"密码"的有 5 条，提到"token"的有 4 条，其中 2 条同时带着 IP 地址。这说明按关键词脱敏，很难既不漏、又不误伤。**我决定第一版先不做脱敏。**

## 决定

### F1：存储

- **用一个全局的 SQLite 数据库**，放在用户目录下，比如 `~/.<插件名>/memory.db`。里面存长期知识（含版本和归档）、按项目共享的摘要，以及原文的全文索引（FTS5，trigram 分词）。
- **只用一个全局库。** 跨项目是这个插件的关键特性。
- **同一时间只允许一个 worker 写库，用文件锁实现。** 多个会话同时运行时，它们的 worker 可能同时裁决同一条全局知识，加锁可以避免互相覆盖。
- **原文不复制进库**，只引用 CC 的 transcript（ADR-0010）。全文索引里存的是渲染后的文本（ADR-0012）。
- **快照文件按项目生成**，由 worker 写（ADR-0015、0017）。

### F2：不做独立库，不加"主体""可见性"字段

我说过，游戏项目只借鉴，不需要和插件统一。没有真实需求，就不提前抽象。代码里自然会有"核心逻辑"和"CC 适配层"的分层，但不做成一个独立发布的库。

### F3：隐私和投毒

1. **第一版不做脱敏。** 原文索引保留原样。检索原文时，密码可能进入上下文，这个风险我接受。**修订 ADR-0016：** 去掉"原文检索要等脱敏做好才能上线"这个前提。
2. **密码不写进记忆。** 这条写进 worker 的提示词，管的是会被注入的长期知识、现状和摘要。
3. **防投毒按来源判断：** 只有我本人的话（ADR-0014 的白名单）能变成规则、约束或偏好。网页和工具输出里的内容，只能作为带日期的观察记下来，不能变成"以后要这样做"。这条也是提示词规则。
4. **只存在本机。** 数据库文件的权限设为只有我自己能读，不同步。

## 理由

- **SQLite 能满足这些需求：** 归档和版本（ADR-0006）、按项目查询、全文检索（ADR-0016），都不需要额外的服务。trace-memory 也是用一个全局的 SQLite 库。
- **单写者是最简单的并发方案。** 写入时裁决（ADR-0013）要先读、再判断、再写，两个 worker 交错执行就会出错。
- **按来源决定信任，比按内容判断更难被利用**（Belief-Based Memory，2606.22030）。而且 ADR-0004 和 ADR-0014 已经限定了"证据只认我本人"，这里只是把它从用户模型扩展到所有会指导行为的知识。
- **脱敏用关键词做不好。** 真实数据里，密码的写法五花八门。为了一个已经接受的风险，现在就做一套容易误判的规则，不值得。

## 后果

好的方面：一个文件就是全部记忆，备份和删除都简单。

要付出的代价和风险：
- **密码可能通过原文检索进入上下文，也可能留在全文索引里。** 归档不删（ADR-0006）意味着一旦有密码写进记忆，它会一直留在历史版本里。以后可能需要一个"彻底清除"的操作。
- **单写者意味着多个会话的 worker 要排队。** 后台任务排队只会带来延迟，不会出错。

## 什么情况下推翻

- 密码实际进入了记忆或注入内容 → 加上写入后的检查和"彻底清除"。
- 我打算把插件发布给别人用 → 必须做脱敏，因为别人不一定接受这个风险。
- 将来真要和游戏共用记忆核心 → 再抽出独立的库，加上主体字段。
