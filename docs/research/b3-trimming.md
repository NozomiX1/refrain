# B3 实验：transcript 里都是什么，送去提取前该裁多少

> 目的：回答 B3。worker 每次都要读 transcript，读多少直接决定成本。先弄清楚里面都是什么，再决定裁什么、留什么。
> 日期：2026-10-23
> 做法：脚本只统计字数，不输出任何原文。脚本放在 scratchpad 的 `b3_stats.py`，没有入库。
> 局限：
> - token 数是估算的（ASCII 字符按 4 个算 1 个 token，其他字符按 1 个算 1 个 token），只适合用来看比例。
> - CC 和 Codex 的历史会话我删过一部分，样本偏少。
> - 只有我一个人的数据。

## 样本

| 工具 | 会话文件数 | 估算总量 | 说明 |
|---|---|---|---|
| Claude Code | 7 | 456 万 token | 不含子 agent。thinking 基本没有以明文存下来 |
| Pi | 166 | 2395 万 token | |
| Codex | 10 | 108 万 token | reasoning 和压缩内容是加密的，统计不到 |

## 1. 组成

| 内容 | CC | Pi | Codex |
|---|---|---|---|
| **我本人写的话** | **0.8%** | **0.7%** | **1.0%** |
| 助手的回复正文 | 10.4% | 1.5% | 3.4% |
| thinking | 0.4% | 1.5% | 0.5% |
| 工具调用（参数） | 22.7% | 13.4% | 25.8% |
| **工具结果** | **37.0%** | **78.9%** | **65.4%** |
| 系统注入 | 26.8% | 0.0% | 3.9% |
| 宿主自己的压缩摘要 | 2.0% | 3.9% | 0 |

各工具的情况：

- **CC 的系统注入里，一半是 `prompt_snapshot`。** 它是 CC 自己用来记账的记录，不是模型实际看到的内容。剩下的是 skill 列表、延迟加载工具的清单、hook 输出等。
- **工具结果主要来自读文件和执行命令。**
  - CC：Bash 占 74%，Read 占 21%。
  - Pi：read 占 67%，bash 占 31%。
  - Codex：exec 占 72%，js 占 28%。
- **工具调用的参数也不小。** CC 里 82% 来自 Bash，因为命令里常常带着整段脚本；14% 来自 Write，因为参数里是整个文件的内容。
- **工具结果是长尾分布。** 超过 2k token 的单条结果，在三个工具里分别占了全部工具结果的 36%、74% 和 77%。单条结果的中位数只有 114 到 388 token。

## 2. 别人怎么裁

- **trace-memory 的默认值：** 每条消息最多 2000 token，每次工具调用最多 100 token，每条工具结果最多 100 token（保留开头和结尾）。每段内容都带地址，worker 需要时可以按地址读全文。
- **Magic Context：** 过时的工具输出按时间自动丢掉，或者由 agent 用 `ctx_reduce` 标记丢弃。

## 3. 模拟裁剪

都只保留我说的话、助手的回复和工具相关的内容；系统注入、thinking 和宿主的压缩摘要全部丢掉。

| 规则 | CC 剩下 | Pi 剩下 | Codex 剩下 |
|---|---|---|---|
| trace-memory 默认值（调用和结果都限 100 token） | 24% | 10% | 17% |
| 放宽（调用限 300、结果限 500 token） | 41% | 25% | 32% |
| **按类型裁**：能重新读到的结果（读文件、搜索、抓网页）只留一个标记；执行类的结果限 200 token；调用限 100 token；我说的话不限；助手回复限 2000 token | **27%** | **9%** | **21%** |

裁完以后，工具调用和工具结果仍然占了一半以上。原因是调用次数多：Pi 有 1.4 万次工具调用，每次哪怕只留 100 token，加起来也不少。
