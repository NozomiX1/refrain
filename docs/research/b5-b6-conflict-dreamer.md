# B5 / B6 调研：冲突怎么处理，第一版要不要 Dreamer

> 目的：B5 回答 worker 写入时，怎么找到相关的旧条目并裁决。B6 回答需不需要一个单独的整理角色（Dreamer）。
> 日期：2026-10-23
> 证据等级：**S** = 源码或项目文档 · **P** = 论文。

## 1. 已经定下的

- **写入时就裁决，不能新旧两条都留着让模型自己挑**（ADR-0006，依据 STALE 论文）。
- **过时的条目归档，不删除**（ADR-0006）。
- **只有 worker 写**（ADR-0009）。

所以 B5 剩下的问题只有一个：worker 怎么看到相关的旧条目。

## 2. 各家的做法

| 项目 | 写入方能看到哪些旧知识 | 超出预算时怎么办 | 有没有单独的整理角色 |
|---|---|---|---|
| **Hermes**（S） | 全部。记忆很小：MEMORY.md 默认上限 2200 字符，USER.md 默认上限 1375 字符 | **由写入方自己合并、腾地方**。工具描述里写着"或者合并来腾出空间" | 没有 |
| **trace-memory**（S） | Noter 能看到注入的知识，素材上限约 20k | 预算**不拒绝写入**，超出的部分交给 Dreamer 收回 | **有**。Dreamer 负责让知识"可读、一致、有效、在预算内"，它"从不创造事实"。触发条件：知识总量超出预算，或待处理的变更累积到约 5k token。它早期有一个"实时整理"的环节，后来废弃了 |
| **Magic Context**（S） | — | — | 有。dreamer 在空闲时整理，还负责用户画像的升级，以及盯住 smart note 的触发条件 |
| **Letta**（S） | 记忆块 | — | 有。sleeptime / reflection 子 agent |
| **CC auto memory**（R） | 主模型自己读 | — | auto-dream 在灰度中，保持 MEMORY.md 在 200 行以内 |
| **mem0 v3**（R） | 检索出来的相关记忆 | — | 没有。**直接放弃了写入时对账**："让模型把能力花在理解输入上，而不是和已有状态做 diff"。冲突改为在检索时按日期挑选 |

## 3. 两条相反的证据

- **支持在一次运行里把提取和裁决一起做完：** Hermes 就是这么做的，结构最简单。
- **支持把两者拆开：**
  - mem0 发现，把提取和对账放在同一次调用里，效果不好；
  - trace-memory 让 Noter 专心提取，整理交给 Dreamer。

  这两个例子都说明，一次调用里做两件事，可能两件都做不好。

## 4. 真实需求（标注实验）

**项目文档会过期**，标注实验里有 3 个案例：
- "以前的文档应该都过期了吧？"
- "这些文档需要整理吗？"
- PROCESS 文档里写着"待用户确认"，其实我早就确认过了。

这是 B6 原本打算让 Dreamer 承担的一项职责。
