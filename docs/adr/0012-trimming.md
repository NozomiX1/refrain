# 0012. 送去提取前的裁剪：原话全留，助手回复设上限，每次工具操作都保留但限体积，注入的内容丢掉

- 状态：采纳（2026-10-23）；裁剪的具体数值见 design.md 4.3 第 2 步；"不裁剪对比"还没测（E7 剩余项，design.md 8.4）
- 日期：2026-10-23
- 相关：[questions.md](../questions.md) B3 · [research/b3-trimming.md](../research/b3-trimming.md) · [ADR-0004](0004-evidence-and-hypotheses.md)（证据只认我本人）· [ADR-0009](0009-writer.md)（worker）· [ADR-0010](0010-extraction-depth.md)（原文是唯一事实来源）· [ADR-0011](0011-v1-scope-cuts.md)（第一版简化）

## 背景

worker 每次运行都要读 transcript，读多少直接决定成本。我统计了自己电脑上 CC、Pi 和 Codex 的真实会话（见 research/b3-trimming.md）：

- 我本人写的话只占约 **1%**；
- 工具结果占 **37%–79%**，主要来自读文件和执行命令；
- CC 的系统注入占 27%，其中一半是 CC 自己的记账记录，模型根本看不到。

Claude 一开始提议按工具类型裁：读文件的结果只留一个标记，执行命令的结果保留开头和结尾。我否决了这个方案：工具调用、读文件都是同一种东西，而且工具调用是轨迹的核心。而且按工具名本来就分不准，Codex 里读文件也是用 `exec` 跑 `cat`。

## 决定

| 内容 | 怎么处理 |
|---|---|
| **我本人的话** | 全部保留，不设上限 |
| **助手的回复** | 保留，每条设上限，初始值约 2000 token |
| **每次工具操作** | 调用和结果合起来算一次操作，**每一次都保留**，只限制体积：参数和输出只保留开头和结尾，标明成功还是失败、原本有多大，并附上回到原文的地址 |
| 系统注入、thinking、宿主自己的压缩摘要 | 丢掉 |

补充三条：

- **按需回读原文。** worker 觉得哪里需要细节，就按地址去读 transcript 里的原文。它读到的，是主模型当时看到的内容，不是磁盘上现在的文件。所以 worker 比主模型慢、文件已经改过了，也不会出问题。
- **裁剪由代码完成，不调模型。**
- **上限具体设多大、失败的操作要不要多留一些，交给实验 E7 来定。** E7 和 B4 一起测：分别用 Haiku 和 Sonnet、裁剪后和全量的输入，在真实会话上提取，比较漏掉了什么、花了多少钱。如果 worker 用 Haiku，成本就不再是主要顾虑，上限可以放宽很多。

## 理由

- **记忆最需要的东西都全留了。** 长期知识的证据只认我的原话（ADR-0004）。主模型读完文件、跑完命令，通常会在回复里自己消化一遍，比如"测试全过了""原因是 X"，所以助手回复就相当于工具结果的摘要。
- **每次操作都保留，是因为它们就是"做过什么"。** ADR-0010 的摘要要用到它们。"能重新得到的不进记忆"（ADR-0003）管的是写进记忆的内容，不管 worker 读什么。
- **丢掉注入的内容，是为了守住 ADR-0004。** 系统注入在 transcript 里大多被记成"用户发的"。不丢掉的话，worker 可能会把 CC 塞进去的东西当成我的原话。
- **裁剪不会丢东西。** 原文一直都在（ADR-0010），裁掉的部分随时能按地址找回来。
- **有先例。** trace-memory 的默认值是：每条消息最多 2000 token，每次工具调用和每条工具结果最多各 100 token，带地址，需要时再回读。在我的数据上模拟，同类规则送给 worker 的内容只有原来的 10%–24%。

## 后果

好的方面：
- worker 每次读的量大约只有原来的一到四分之一，具体取决于上限。
- 规则简单，不需要按工具分类。

要付出的代价和风险：
- **worker 可能不知道自己漏看了什么。** 比如命令输出里藏着一个环境上的坑，而助手的回复里没提到它。标明成功还是失败、原本有多大，能帮 worker 判断要不要回读，但不能保证它一定会去读。这个风险由 E7 来量化。
- **要识别哪些是注入的内容。** 这和 B8（怎么判断哪些话是我本人写的）是同一个问题，各个宿主的格式还不一样。

## 什么情况下推翻

- E7 发现裁剪后的输入，比全量明显漏得多 → 放宽上限，或者改用 fork 读完整的上下文（B4）。
- worker 用 Haiku 以后，全量输入的成本也可以接受，而且质量不差 → 放宽到几乎不裁，只丢掉注入的内容。
