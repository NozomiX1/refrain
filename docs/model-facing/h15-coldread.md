# H15 冷读者检查（2026-10-25）

找两个对项目一无所知的子 agent，只给它们模型实际会看到的文字（成品里分隔线以下的部分，不带我们写给自己的注释），让它们照着做一遍，再标出看不懂、拿不准、可能理解错的地方。

- **主模型那份**（Opus）：简报、工具说明、工具返回样例、压缩后的内容。给了 5 个场景："接着上次那个方案做""记住：以后提交信息用英文""K9 不对""Lute 里 Wine 怎么配的""压缩后说继续"。
- **书记员那份**（Haiku）：系统提示和输入样例，要求真的整理一遍，写出完整的 submit。

两份报告各列了十几条。下面先去掉因为样例数据拼凑没对齐造成的（M12 在两个样例里内容不同、K30 对不上、新会话的样例里出现"本会话现状"），只记值得改的。修改全部已经做了。

## 书记员那份

| 发现 | 改法 |
|---|---|
| **把一次性的话扩大成了长期规则**：样例里一句"先别提交，我再看一眼 diff"，被它改写进 K3，成了"以后提交前都要先等用户看 diff"。提示词里已经写了"不扩大范围"，它还是犯了 | 新增"只针对这一次的话，不写成规则"，用这个例子；只有用户说了"以后""每次""总是""都要"或明确让它"记住"，才写成规则 |
| 提示词没说"你是谁"，它自己也是 Claude，分不清"Claude"指谁 | 开头写明：你是后台整理记忆的助手；下文的"Claude"指被记录的编程助手，不是你 |
| Claude 断言的事实和工具输出对不上时，没有规则 | Claude 说的事实只是它的说法，和工具结果对不上时以工具结果为准，无法核实的写成"Claude 说……" |
| "你说的我都同意了"的范围不清，同一句里还改了数字 | 概括性的同意写清是哪几项；同一句里有调整的，按调整后的写 |
| "证据扎实"没有门槛 | 推断要在至少两次彼此独立的场合出现过；复查一致就补出处，不一致就改写或归档 |
| "仓库文档对不上"这条规则执行不了，它读不到仓库 | 只在对话里明确出现了文档内容时才加待办 |
| 设计决定写不写进知识，和"仓库文档不复制"冲突 | 已写进文档的，一句结论 + 去哪看；只在对话里定下的，写成知识 |
| 小问题："五个方面"后面列了六项；"截至"的日期什么时候刷新；待核实和待定的边界；"打断"什么意思；"摘要不交给以后的会话"和"压缩时交给 Claude"读着矛盾；`condition` 写 null 还是省略 | 逐条改了措辞或补了例子 |

## 主模型那份

| 发现 | 改法 |
|---|---|
| 本会话现状里的授权和长期规则 K3 冲突，不知道听哪个 | 简报开头写明优先级：用户刚说的 > 本会话现状 > 长期知识 |
| 改了记忆以后，简报里一直显示旧内容，可能还照旧做 | 简报开头写明：纠正过的记忆在更新前以用户刚说的为准 |
| "记住"的规则只写在 search 的说明里，不一定会联系起来 | 简报开头也写一句（陈述句，不用命令语气） |
| "每条都能追溯到原话"和〔推断〕自相矛盾 | 改成"每条都附有出处"；〔待定〕、条件、"截至"各补一句含义 |
| 不知道编号是否全局唯一；S/T/E 只解释了 T；工具结果算不算新的一轮；大小写、项目名是否参与匹配 | read 的说明里写明编号全局唯一、S/T/E 的含义、工具结果不算用户消息；search 写明不区分大小写、项目名不参与匹配 |
| 压缩后：简报块有没有刷新、和保留的对话对不上听谁、只有标题的摘要怎么办、附加说明是不是要它做什么 | 交接开头逐条写明；附加说明写成"供你参考" |
| 现状条目里有项目内部叫法（简报、交接、H14），要先去查 | 书记员提示词加一条：不常见的项目术语附上摘要编号或文档位置 |
| 小问题：分组里的"（2 条）"指什么；记忆库读不到时"这次"指什么、要不要告诉用户；"约 700k"缺单位 | 改了措辞 |

没有改的：主模型能看到 submit 的完整参数格式，读者觉得是噪音。参数格式是工具注册时一起给出的，藏不掉；说明的第一句已经写了"仅供后台整理记忆的子任务使用"。这一项按 7.8 的约定，等实际运行再看。

## 第二轮（同一天，新的子 agent 读改过的文字）

**最关键的修复有效。** 同样的输入，Haiku 这次一条知识都没写，理由是"'先别提交'和'可以提交了'只针对这一次，已经结束"。第一轮报过的问题（优先级、记住、编号、地址、待定和待核实的区别、项目术语附线索），两份报告都说已经清楚。

剩下的都是小补丁，已全部改掉：

- **类别显示名**："理解"改成"背景和决定"（字段值 `understanding` 不变）。Opus 两轮都说它含糊，还把归错类的设计决定当成了给自己的规则。提示词里写明：本项目正在做的东西的设计决定归这一类，规则是 Claude 自己做事要遵守的。
- **主模型那边**：交接里"以对话为准"也适用于本会话现状；本会话现状的定义加上进行中的事项；简报写上项目名；〔推断〕把握较低；"不写文件"包括 Claude Code 自带的记忆文件；改记忆时同一条回复里核对并说明，只改一部分时复述理解；统一叫"后台整理"；submit 说明再加重；几处措辞。
- **书记员那边**：独立场合的定义；没说原因的打断、拒绝只记操作；待核实放项目现状还是本会话现状；工具只查了一部分时不能证明"最新""全部"；接续指同一个具体话题；这一批里新出现又结束的事项不写；问句提的调整怎么算；授权照原话写清范围和有效期；字数按字符算。
- **样例数据**：几个文件里 M 编号对不上的地方统一了，K12 改归"背景和决定"。

**冷读不完全干净：** 通用子 agent 会带上外层会话的 git 状态和记忆索引（Haiku 自己指出了）。这次影响不大。正式实测要用我们注册的书记员 agent 类型来跑：它设了 `omitClaudeMd`，系统提示也是整个替换的。

## 第三轮：找"装不下"的地方（同一天）

前两轮冷读找的是"看不懂"，没发现"证据来源只有原话和推断，装不下工具输出里看到的经验"这种漏洞。所以第三轮换了查法：

- **书记员压力测试**（Haiku）：5 段专挑边角的对话（操作失败后换法成功、一次性的话和长期规则混在一句里、部分纠正加合并加改口、无项目会话里的密码和私人信息、新会话重提旧待办加未答复的提议），要求报告哪里卡住、哪里必须违反规则才写得下去。它做对了观察、一次性和长期的区分、临时标签、凭据、私人信息、未答复的提议。
- **设计一致性审查**（Opus，允许读仓库）：以 `epistemic` 那个漏洞为例，自己构造了约 25 个场景，找"表达不了""文档互相矛盾""流程断点"三类问题。

改了的（我同意了全部建议）：

- **原样保留的现状项只写 `{"from": n}`**，类型、内容、条件、出处、日期由代码照搬。原来要求原样保留的授权带出处，可书记员看不到旧出处，只能编或者丢掉。
- **"什么时候写成规则"合成一条**：明确只针对这一次的放现状；没有时限的纠正和禁令写成知识；"以后""记住"是更明确的信号，不是必须出现的词。
- **`condition` 只放"要等的前提"**，授权的有效期写进内容。原来"PR 合并之前可以直接 push"会被主模型读成"合并以后才能 push"。
- **原话的校验按写入后的完整出处查**（K 编号展开、并上旧出处之后）。
- **主模型如实说能做到什么**：摘要和原文改不了（写错的摘要由书记员写一份"更正 M34"）、归档后仍能检索、凭据不会被记住、"这个别记"只管记忆不管原文。
- **证据来源再扩**：用户陈述的事实算原话；用户转述、粘贴的别人的说法算观察；用户认领粘贴内容并要求照做的，认领的部分算原话。
- **别的项目的条目**：用户点名的可以改；新建只能在当前项目或 global；判断不了属于哪个项目的不写成知识。
- **本会话现状不跨会话升级**：只有项目现状能"之后的会话里又说了一遍就升级"；授权要用户在会话里明确说长期有效才升级。
- **授权和临时指令不能放项目现状**，校验时退回。
- **有时效的个人情况**写成知识并写明到哪天，过期归档。
- 小补丁：update 可以改作用域、类别、证据来源、待定；合并取更小的作用域、更低的把握；"同一件事"要对象和做法都一样；新知识和现状冲突时改那一项；教训加做法的归参考，机器环境的观察用 global；about_me 的判断标准；新建前先搜一下以前的知识（含已归档）；书记员忽略 search 说明里写给主模型的段落；无项目会话的检索范围；术语表、样例、"截至"日期的说法统一。

没覆盖到、记进 7.8 实现时验证的：fork 时本会话现状怎么继承（4.5）、项目改名或搬目录（6.1）、回退对现状和临时标签的影响（6.4）。
