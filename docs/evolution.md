# refrain 的设计演变

> 推翻过的方案和关键决策：原来怎么想、发现了什么、改成了什么。现在的设计以 [design.md](design.md) 为准，这里只讲"怎么走到这一步"。逐日的完整讨论在 [log.md](log.md)，设计阶段的正式决定在 [adr/](adr/)，实验数据在 `experiments/*/README.md`。
>
> 每条的格式：**原来** → **发现** → **改成**，最后是出处。日期是 2026 年。

## 注入：简报怎么交给主模型

**切片注入 → 一个自定义块 → SessionStart**
- 原来：把简报切成几片，用几个 hook 分别注入（ADR-0015）。
- 发现：几个 hook 并行执行，片的顺序不固定（D-a）。改用 mod 的 `prompt.context` 自定义块（D-a3）以后，s1 第三次演练又发现它是给**每一段对话**的：CC 用它放 CLAUDE.md，书记员子 agent 收到了一份写给主模型的简报，Explore 之类的子 agent 也收到了记忆，违反 ADR-0019；它又不告诉我们是哪段对话。先试过"按时间猜哪次是书记员的"，我觉得太 hack，否掉了。
- 改成：`classic.SessionStart` 的 `additionalContext`。它只有主会话有。当初没选它，是因为官方文档说 hook 注入上限 1 万字符；e2 探测检查实际发出的请求，1 万、3 万、10 万字符都一字不差，子 agent 一段都收不到。代价是恢复会话时 SessionStart 也会触发，要自己跳过，否则重复。
- 出处：ADR-0015、design.md 4.1、`experiments/e2-sessionstart/`、log 10-26。

**简报文件 → 每次现渲染**
- 原来：书记员每次写完，把每个项目的简报渲染成文件，注入时读文件（5.4）。
- 发现：改走 SessionStart 以后，注入时直接调用核心程序现渲染（约 0.14 秒），文件没人读了，却还在每次整理后重写。是 10-26 审计设计文档时发现的。
- 改成：删掉简报文件。
- 出处：log 10-26（审计）。

## 压缩

**CC 原生压缩 → 拼交接，不调模型**
- 原来：CC 压缩时调模型写一份总结，要等二三十秒，总结里丢东西（D3：丢了待办、会话内授权、项目目标）。
- 发现：mod 能在 `session.compact` 里直接替换上文（D-b），拼一份交接只要 5 毫秒。
- 改成：交接 = 本会话的摘要 + 书签之后的原文尾巴，简报由 SessionStart 重新给。
- 出处：ADR-0009、D-b、design.md 4.4。

**原文尾巴：渲染后的文字 → CC 原本的消息**
- 原来：尾巴和书记员的输入共用一套渲染、裁剪。
- 发现：我指出主模型要的是接着干活，刚读过的文件、刚看到的报错要完整，工具调用和结果要成对。
- 改成：直接从 `e.messages` 里截下 CC 原本的消息放回去。顺带避开了核心程序 stdout 4 MiB 的限制。
- 出处：log 10-25、design.md 4.4。

**最后一轮总是原样保留**
- 原来：只保留书签之后的部分；书记员追上了，尾巴就是空的。
- 发现：实现时发现这样压缩后模型手上只剩摘要，刚问的问题、刚读的文件都没了。
- 改成：最后一轮总是原样保留。这是实现时我自己加的，事后告诉你；你同意，说一般的压缩都会保留最后几轮。
- 出处：log 10-26。

**压缩后最近一次整理被误撤销（bug）**
- 发现：s1 第二次演练，压缩后书记员的书签被判成"已回退"，最近一次整理被撤销后重做。原因是 CC 把保留的尾巴用新 uuid 抄一遍时，**工具结果的副本把"上一条"指回了压缩前的原件**（`sourceToolAssistantUUID` 原样照抄，像一个浅拷贝），读取器顺着它绕过了压缩边界。
- 改成：往回走时遇到这种副本（时间戳早于边界），直接跳到那个边界。在真实 transcript 上验证过。
- 出处：design.md 6.4、`experiments/s1-drill/`。

**自动压缩：写设置关掉 → mod 拒绝**
- 原来：CC 的自动压缩之后，引擎把旧的简报块原样放回去（D-a4，CC #92949），所以要关掉；做法是往项目的 `.claude/settings.local.json` 写 `DISABLE_AUTO_COMPACT=1`。
- 发现：要动我项目里的文件；CC 只在启动时读它，项目的第一个会话不受保护。换成 SessionStart 以后，e2 测到一轮中间的自动压缩仍会新旧两份并存。
- 改成：mod 在 `session.compact` 里认出 `auto` 和 CC 自带空闲压缩的 `idle`，直接拒绝，提示一次。
- 出处：design.md 4.4、log 10-26。

**空闲压缩：CC 自带 → refrain-timer**
- 原来：用 CC 自带的 `idleCompaction`。
- 发现：它的条件由 CC 定。mod 在自己的计时器里发起压缩，会绕过自己的 `session.compact` hook，变成原生压缩（e0 C6）。
- 改成：配套一个十几行的小插件 refrain-timer，由它发起压缩，refrain 的 hook 照常接管，实测 0.2 秒。条件：缓存过期后、上文 ≥ 6 万 token、交接不超过上文一半。
- 出处：design.md 4.5、`experiments/e0-probes/`。

**积压太多时交给原生压缩**
- 原来：交接整段放进原文尾巴，不设上限。
- 发现：问到"每批上限超了怎么办"时想到：书记员积压很多时，尾巴几乎就是整个上下文，压了等于没压。
- 改成：估算的交接超过上下文的一半，就交给 CC 原生压缩，和空闲压缩同一条规则。记忆不受影响，书记员之后照样追上。
- 出处：design.md 4.4、log 10-26。

## 书记员

**怎么运行：fork / `claude -p` / `$.model.complete` → 注册一种子 agent**
- 原来：考虑过 fork 主会话（继承上文）、起 `claude -p` 子进程、直接调模型。
- 发现：fork 的上文我们控制不了，模型也必须和主会话一样；`claude -p` 太重，还要防递归；`$.model.complete` 不能用工具，没法检索、没法提交后被退回重交。
- 改成：mod 用 `$.agent.register` 注册书记员子 agent，替换系统提示、只给三个工具、对主模型隐藏，每次 `$.agent.spawn` 在后台起一个。
- 出处：H7、design.md 4.3 第 4 步。

**收尾从来没执行过（bug）**
- 发现：s3 演练里看到书记员的用量一直是空的。原因是 mod 的 API 规定：从某个 hook 里 `$.agent.spawn` 起的子 agent，它的事件会跳过那个 hook。书记员在主会话的 `turn.complete` 里起，它自己的 `turn.complete` 就到不了这个 hook。s1、s2 时就是这样：用量一直没记（状态栏 ≈$0.00），没提交就结束的运行要等 20 分钟超时才算失败。
- 改成：收尾拆成单独的 hook。同一事件注册两次要带匹配条件，于是用了一个列出全部结束原因、什么都不过滤的条件。加进 CC 自检清单第 8 项。
- 出处：`experiments/s3-scribe-step/`。

**提交后代答，省掉"完成"那次请求（试过，不行）**
- 原来：书记员提交后，CC 还要再调一次模型让它收尾，这次请求把它的思考和提交当新输入再写一遍缓存，约占一次整理的 13%。想在 `turn.step` 里代答这一步。
- 发现：2.1.310 要求子 agent 调用 `SubagentHandback` 交回报告才算结束。代答空回答，CC 补一句"报告还没交"再请求；代答一个 `SubagentHandback` 调用，CC 不执行。
- 改成：不做。加进 CC 自检清单第 9 项。
- 出处：`experiments/s3-scribe-step/`。

**模型和推理强度：继承 xhigh → Haiku low**
- 原来：书记员没设推理强度，继承了我全局给 Haiku 设的 xhigh，每次输出 8k–16k token，大多是思考（s1）。
- 发现：E7 在真实会话上重放：Haiku low 的答题分（问答 8.7、任务 4.3）和 Sonnet medium（9.0、4.5）在几遍之间的波动以内，都没有"没依据"的知识；额度是 Sonnet 的 1/7。
- 改成：Haiku，推理强度固定为 low。
- 出处：`experiments/e7-scribe/`。

**触发量：试 6 万字，留 2 万字**
- 发现：一次整理的输出量和这批对话多大无关（48 次，7 千到 2.9 万字，相关系数 −0.05），所以想用少整理几次来省。6 万字确实省约 45% 额度，分数没掉，但知识少了约四分之一，也更容易交白卷。
- 改成：保持 2 万字。按绝对值算，整理两天的密集讨论只用周额度约 0.3%，省下的不值得换知识变少。
- 出处：`experiments/e7-scribe/`。

**每批上限：12 万字 → 5 万字**
- 原来：按每字约 0.65 token 估，12 万字的一批不会越过 Haiku 单次请求 10 万 token 的价格线。
- 发现：E7 实测渲染后的输入每字 0.62–0.94 token（平均 0.77），12 万字加上指令和知识会越线；批次越大也越容易交白卷。
- 改成：5 万字。按最坏情况、知识涨满上限也在线内。上限只在积压时起作用。
- 出处：`experiments/e7-scribe/`、design.md 4.3。

**允许交白卷 → 至少一份摘要**
- 原来：对话没什么值得记的（几句"好的"），可以交空结果。
- 发现：E7 里书记员两次收到 2.4 万字和 6 万字的对话，只想了几百 token 就交了空结果，说"输入里没有要处理的对话"，校验放行，那一段没留下摘要和知识。
- 改成：每次至少写一份摘要，提示词里说明对话在输入最后一节、每次都有内容，校验不过就退回。
- 出处：`experiments/e7-scribe/`、design.md 6.5。

**按稳定性排序来命中缓存（没起作用）**
- 原来：书记员的输入按"越稳定越靠前"排，摘要按 K 份一批折叠，指望反复运行时命中前缀缓存。
- 发现：E7 的 131 次整理，第一次调用读到的缓存都恰好是 14,306 token，也就是指令和工具说明。整份输入是一条消息，CC 只在末尾打断点，前面相同也对不上；真实使用时两次整理隔 13 分钟到 10 小时，子 agent 的缓存只有 5 分钟。
- 改成：不再为缓存下功夫（上限约省 15%），排序留着，它不花成本。省额度改从思考输出下手（占一次整理的约六成）。
- 出处：`experiments/e7-scribe/`、design.md 4.3。

**关掉的会话剩下的尾巴：写了，没做 → 补上**
- 原来：设计写着"由同一项目下一个会话的书记员补上"。
- 发现：问每批上限时查到这条没实现，核心程序只整理当前会话，每个会话最后那段不到 2 万字的对话一直没人整理。
- 改成：当前会话不够阈值时，补同一项目里 1 小时没写入的会话的尾巴，不管多少。判断错了没有代价，书签按会话各记。
- 出处：design.md 4.6、log 10-26。

**"项目现状要短"**
- 发现：e1 切点 1，书记员写了 31 项项目现状，有提交号、测试数、环境配置，作答时噪声很多。
- 改成：提示词加一条"项目现状要短"（十项左右，背景事实改写成参考类知识），重跑变成 13 项。
- 出处：`experiments/e1-ablation/`。

## 检索

**search 结果标时间，而不是标"最新"**
- 发现：e1 里作答的模型读到一份早期摘要写着"用户没有直接回复"，没注意到后面已经定了。
- 改成：我提议每条结果带时间（精确到分钟），比"最新"标记信息多。
- 出处：design.md 4.7、log。

**模型不去查，是问法的问题，不是缺规则**
- 发现：e1 切点 A、B，有简报的模型四次作答一次都没查，丢分全是"不知道"。试了加"什么时候查"的说明、加规则，都没用；把开头的"确认你还记得多少"换成中性的"用户问了下面几个问题"，就去查了，分数从 8.5 / 7 到 9.5 / 10。
- 改成：没有证据的规则不加进简报；以后的评测一律用中性问法。
- 出处：`experiments/e1-ablation/`。

## 存储

**锁：文件锁 → 数据库里一条"正在运行"的记录**
- 改成：在立即事务里检查和插入，超过 20 分钟没收尾算失败。少一个文件，锁和写入在同一个地方，进程崩溃也不会留下死锁。实现时我自己定的。
- 出处：design.md 4.3、log 10-25。

**同一次提交里先更新再归档同一条，版本号撞车（bug）**
- 改成：一次提交里同一个编号只能出现一次；版本号越过作废的版本往后编，加了唯一约束。
- 出处：design.md 6.5、log 10-25。

**知识超预算就合并、归档 → 只是提醒线，全部注入**
- 原来：ADR-0013 设了硬上限，超了由书记员合并或归档。
- 发现：合并要同时理解多条知识，经常要回头看原文，容易改错；少放的代价可能致命（漏掉硬约束）。
- 改成：4k / 15k 只是提醒线，知识全部注入；真装不下时再"注入时挑着放"。
- 出处：design.md 5.5。

## 读取器

**粘贴的结束标签带编号**
- 发现：s2 第一次用真实录下的 transcript 做测试样本，查出粘贴的结束标签是 `</pasted_content id="…">`，原来的规则只认不带编号的，粘贴的内容会被当成我的原话。手工构造的样本没有覆盖到。
- 改成：规则改成认带编号的标签；测试样本改用 tmux 录的真实会话，清理后入库。
- 出处：`experiments/s2-fixtures/`。

## 成本和额度

**按 API 价估额度，差了一倍**
- 原来：开销都按 API 价折算（含缓存读取），以为能用它估订阅额度。
- 发现：E7 开 11 组并行重放，40 分钟用掉 5 小时额度的九成多、周额度 9%（约 $15）；可上周 $248 才用 78%，对不上。wokey.ai 对几百个订阅账号的实测：缓存读取几乎不扣额度，缓存写入和输入差不多。去掉缓存读取重算，两边对上了（满周约 $75–90），额度没被砍。我的主会话 90% 以上是缓存读取，所以平时显得耐用；`claude -p` 每次都整段写入、再加思考输出，扣得重。
- 改成：估额度只算输入、缓存写入和输出；实验最多同时跑两组。
- 出处：`experiments/e7-scribe/`、log 10-26。

**开销比的口径：API 价 → API 价加额度口径**
- 原来：ADR-0021 定为按 API 价算（我否决了按额度算：额度换个套餐就不适用）。
- 发现：主会话的 API 价大半是缓存读取，按 API 价算的"书记员 ÷ 主会话"会低估书记员在额度里的占比。
- 改成：保留 API 价，再加一个只算输入、缓存写入和输出的额度口径〔待实现〕。
- 出处：ADR-0021、log 10-26（审计）。

## 测试和工程

**核心测试改名为 `*.spec.ts`**
- 发现：CC 的 `claude plugin test` 会把目录下所有 `*.test.ts` 当成 mod 测试来跑，核心程序的测试在 mod 环境里加载不了。
- 改成：核心测试叫 `test/*.spec.ts`，mod 测试放 `hooks/test/*.test.tsx`。
- 出处：log 10-26。

**状态栏：每轮读整个 transcript → 只读新增的部分，3 秒刷新**
- 发现：状态栏脚本每次都把 transcript 读一遍算 token，132 MB 的要 1.3 秒，超过 CC 给的 1 秒就会被作废。定时刷新每秒一次占一个核约 10%。
- 改成：记住读到哪、只读新增的部分（每次几毫秒）；我选了保守一点，3 秒刷新一次。
- 出处：design.md 7.11、log 10-26。

**CC 版本固定**
- 发现：`~/.claude.json` 的 `autoUpdates: false` 对原生安装的 CC 不起作用，一直在自动升级。
- 改成：设 `DISABLE_AUTOUPDATER=1`，固定在 2.1.310，手动升级后跑自检。
- 出处：design.md 7.13。
